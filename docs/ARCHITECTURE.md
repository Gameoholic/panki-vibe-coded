## Where we actually are

**Steps 1 to 13 are built:** decks, cards in a deck, flipping through a deck, the mark with its opening moment, the navigation (a hub behind a Home tab, a Settings tab), a deck's settings (rename, delete, its SRS type), card types (what fields a card has and what each holds; every deck is made with one), the SRS (step 8): SRS types with their stages, answers and rules, a review that shows what's due and answers that move the card, and the settings that run every review; then, together on 2026-10-10, the silo (step 9: sittings, every answer's seconds, a ledger of everything else), signing in (step 10: one database per account, a ten-year cookie, accounts from the terminal), the Review door lit only with something to do (11), the Stats tab (12) and the home's tiles (13); themes (14); and media on cards (step 15, 2026-10-11: a field can hold a sound, a clip or a picture, the file kept beside the account's database), the first of the five steps that lead to the extension (the plan and its build brief: https://claude.ai/artifact/D3jDa6x2TLya8Z68geVBZc); and the extension itself (steps 16 and 17, 2026-10-11, built together at the owner's ask and **never run by Claude**: a browser extension that adds a word from a YouTube caption or from any page's selection, with the line's own clip); and changing and deleting a card from its deck's list (step 18, 2026-10-11). On 2026-10-17, at the owner's "ok implement everything": AI subtitles (a video transcribed by ElevenLabs Scribe v2 through the API, following the viewer in the extension; "Transcribing a video"), with an admin flag on accounts and a shared store for what every account shares (`shared.sqlite`), built in one go and never run. Everything below describes that, and nothing more exists.

## Shape

A pnpm workspace on Node 22 (`>=22.13`, where `node:sqlite` needs no flag):

| `apps/api` | Express 5 + TypeScript, SQLite through `node:sqlite`. Run with `tsx` (dev and prod), no emit. | `pnpm dev` → 127.0.0.1:3001 |
| `apps/web` | React 19 + Vite + TypeScript. The dev server proxies `/api` to the API. | `pnpm dev` → http://127.0.0.1:5173 |

It imports the contracts and the web's own components and styles as source (`@web/*` → `apps/web/src`), so a card, a button and a colour are the same thing in both. | `scripts/verify.mjs` (with `scripts/lib/scratch.mjs`, the scratch instance and the Chrome driver) | Drives the real UI in headless Chrome on a scratch instance. The owner's to run; Claude never does. | `pnpm verify` |

Environment (everything that differs between the owner's instance and a scratch one): `PORT` (API, default 3001), `PANKI_DATA_DIR` (default `apps/api/data`), `PANKI_WEB_PORT` (default 5173), `PANKI_API_PORT` (what the web dev server proxies to, default 3001), `PANKI_TIME_ZONE` (the owner's clock, for when a day turns over; default the machine's own zone, and a wrong name fails at startup — the VPS may run on UTC while the owner lives on Israel's), `PANKI_FORVO_KEY` (a Forvo key for word audio, used by any account that hasn't typed its own in Settings; none by default).

## Data model

**Every account is a whole Panki of its own.** `PANKI_DATA_DIR` holds `auth.sqlite` (who the accounts are and which devices are signed in) and `users/<userId>/`, one folder per account and the whole of it: `panki.sqlite` and, beside it, `media/<mediaId>` (the files its cards hold, one per id, no extension; `dbs.ts` → `mediaDirFor`) and `dictionaries/<id>` (the dictionary zips it keeps on Panki for the extension; `dictionaryDirFor`). Each database is opened by the same `openDb` (migrations, the built-in SRS types) the first time that account makes a request (`dbs.ts` → `createDbs`: `dbFor(userId)` opens lazily and keeps the handle, `closeAll()` at shutdown). All WAL mode, foreign keys on. Accounts are made only from the terminal: `pnpm user:add <name> <password>` (the password on the command line, the owner's choice; at least `PASSWORD_MIN` characters), `pnpm user:password <name> <newPassword>` (signs every device of that account out, the standard safeguard, and records the time in `password_changes`), `pnpm user:list`, and `pnpm user:admin <name>` / `pnpm user:admin <name> off` (makes an account an admin, one that changes what everyone shares, or takes it back; `User.admin`, carried by `/api/me` and the sign-in's answer, and refused with `403` by `session.ts` → `requireAdmin` on the routes marked admin-only below) (`apps/api/src/cli/users.ts`). **The first account adopts the data from before accounts existed:** when `add` makes the first user and `PANKI_DATA_DIR/panki.sqlite` is there, it is moved (with its `-wal` / `-shm`, `renameSync`, never copied) into that account's folder and the command says so; Windows refuses to move a file the running API holds, so the command prints "Stop `pnpm dev` first, then try again." and makes no account.

`auth.sqlite` (its own short migration list in `authDb.ts`, same `user_version` pattern):

```

  token_hash     TEXT NOT NULL UNIQUE   -- sha256 hex of the cookie's secret

  user_agent     TEXT NOT NULL      -- the browser's whole description of itself
  device         TEXT NOT NULL      -- the same in the app's words ("Firefox on Windows"), device.ts

  id, at, name, ok (0|1), address

  id, user_id REFERENCES users(id), at

  id, user_id REFERENCES users(id), admin (0|1), at
```

**A sign-in that isn't the app's (step 16).** Something that can't keep the app's cookie, the browser extension, signs in with the same name and password and `bearer: true`: the answer carries the session's secret itself and no cookie is set, and from then on it sends `Authorization: Bearer <secret>`. `requireSession` takes either (`session.ts` → `secretOf`); the row is a session like any other, so it's listed with the devices in Settings (its `device` reads "Panki extension · Chrome on Windows", from the `client` it named) and signed out the same ways. Nothing else about the API changes for it: no CORS is opened, because the extension's own pages and worker are let through by the browser once the owner has allowed Panki's address, and a page's script never calls the API at all.

Why: **the cookie carries a secret the database never holds** (32 random bytes, base64url; `panki_session`, `HttpOnly`, `SameSite=Lax`, `Path=/`, ten years, `Secure` when the request came in over https: `trust proxy` is `loopback`, so nginx's `X-Forwarded-Proto` counts and `req.ip` is the browser's), the row keeps its hash, so the file alone signs nobody in. Passwords are scrypt (N 2^15, r 8, p 1, a 16-byte salt, a 64-byte key; Node's own, no dependency) and the stored string carries its parameters, so raising the cost changes only new hashes. **A wrong sign-in and an unknown name are the same answer** and take the same time (the unknown name is checked against a dummy hash). **Five wrong tries from one address inside fifteen minutes** and that address waits a minute (`throttle.ts`, in memory). Nothing about a password or a token is ever logged.

**What every account shares** lives in `shared.sqlite` (`shared.ts` → `openShared`, its own migration list, the same `user_version` pattern; opened once at startup, closed at shutdown): the keys for the services Panki calls, the dictionaries kept on Panki, how transcribing runs and every transcript. Anyone signed in reads it; an admin alone changes it. Its dictionary zips live in `shared/dictionaries/<id>` under the data folder (`mediaFiles.ts` → `sharedDictionaryDir`). Until 2026-10-17 the Forvo key and the dictionaries were each account's own; at startup `shared.ts` → `gatherShared` moves what accounts still hold over (the first Forvo key found becomes everyone's, a second account's that differs is left where it is and said in the log; each dictionary's zip is moved with `renameSync`, copied then deleted across file systems, and its row made under the same id, `uploaded_at` and `uploaded_by` the account's; one whose title is kept already is let go, its zip deleted, as a copy of a file the owner has; one whose zip is missing is marked and nothing moved), marks every row it has dealt with (`dictionary_files.moved_at`, a `'moved'` row in `forvo_key_changes`) so the next start moves nothing, and logs one account's trouble without stopping the API.

**The stitch** (`shared.ts` → `insertPiece`, one transaction with the piece and its words). The extension cuts pieces where nobody is speaking, but a forced cut or a jump makes two pieces that overlap by a second or two, both hearing the word at the edge. By geometry alone: a word's depth in a piece is its distance from the nearer edge; for every living word of another piece that begins inside the new piece, the new piece wins when it heard that moment deeper, and the old word gets `removed_at`; for every new word that begins inside another kept piece, the old piece wins when it was at least as deep, and the new word is written with `removed_at` set as it lands. Exactly one survives at each moment, and nothing is deleted. The transcript read back (`transcript`) is the living words in order, each as its latest fix (`heard` carrying the engine's word only when a fix changed it), with `covered`, the kept pieces' stretches and the quiet listened through (`transcript_quiet`) merged where they overlap or come within 100 ms. A piece the engine wrote in another language (`keepHeard`: not `jpn` or `ja`, with words) is stored with `kept = 0` and no words, so it costs once and is never sent again (one asked the language that heard no words is kept: a stretch where nothing was said); `secondsTranscribed` sums every piece, kept or not, for the Settings' count.

**The silo** (the owner's words: "total surveillance"): everything that happens is kept with its timing, needed now or not. The API stamps every time; the browser only ever sends spans it measured on its own clock (`thinkMs`, `decideMs`, `shownMs`), never a time. What's frozen on an answer's row (`miss`, the spans, the sitting) is read back as it was; what a card *is* (its place, its due time) is still derived live. **The stats are worked out on every read** (`db.ts` → `stats(deckId | null, now)`, JS over the rows) for the living decks in scope: the windows are the owner's days (`time.ts` → `dayOf`, the calendar date in `PANKI_TIME_ZONE` once the clock is wound back by the Settings' `dayStartHour`; `addDays`, `daysBetween`, `weekdayOf` on the day keys), so a clock change moves nothing; a card overdue counts as due today; the week runs Sunday to Saturday; the twelve weeks of `added` end with the one that began on the most recent Sunday. The definitions of each number are the `Stats` schema's comments in `packages/contracts/src/history.ts`.

Why: the **browser mints the id** so a retried POST (a flaky phone connection) returns the row that already exists instead of creating a second one (`INSERT OR IGNORE`, then read back). **`created_at` comes from the API's clock**, never the client's — the server is the authority on time. A deck's **card count** and a type's **deck count are derived** in the query on every read, never stored. **A card is its values:** the deck's card type says which fields exist, which are the front, which must be filled; the card holds one value per field (`cardProblems` in the contracts is the rule, run in the browser before sending and in the API at the boundary). **Delete hides, never destroys:** it sets `removed_at`, every query the app reads through filters removed decks, cards, types, fields, stages and answers out (so a removed deck's cards are unreachable too), and nothing is ever `DELETE`d. **A deleted card (step 18) is out of everything from the moment it leaves:** the deck's list and counts, what a review shows, the ladder, "coming up" and "added" in the stats, and whatever is later done to its deck's cards (a switch of SRS type and a stage taken away move only the cards still there, so a restore, when one is built, has to seat such a card afresh). What it was answered stays in the history: its answers still count among the reviews, the streak, the heat map and the time, because they happened; it just isn't named among the toughest cards any more (`selectScopeAnswers` carries `living` for that). Only an insert's read-back still sees a deleted card, so the same id sent again is the same card and never a second one. Its files stay where they are. Removing again keeps the first time; a type a deck uses can't be removed at all. **Renaming records what it changed from and to** (`deck_renames`, `card_type_renames`), inside one transaction with the update; the same name again changes and records nothing. Updating a type takes the whole field list: ids it knows are updated (and un-hidden), new ids added, ids left out hidden; an SRS type's stages and answers work the same way.

**A card stores nothing about its schedule but its answers.** Each answer (and each move made for it) is one `card_places` row: when, which answer, where it was, where it went. Its place is the last row; its **due time is derived on every read**: the last answer's time plus the wait its place has *now* (the stage's wait, or the ask-again's), spread ±10 % by a hash of the row id when the setting is on (`dueAt` in the contracts). Nothing stored goes stale: editing a type changes only what happens next, and the past stays as it was. The place is by **stage id**, not by number, so reordering stages moves no card; `past` counts rungs beyond the top for a ladder whose wait repeats or grows there. **The first stage waits like any other** (the owner's change, 2026-10-10; before that it never waited): it is where a new card stands (its rung is 0 before any answer), and a card kept on it or sent back to it comes back after its wait, ten minutes in the starters. **The SRS types that come with the app are rows**, marked by `srs_types.builtin` (which starter they are; `builtin: true` on the type as read). `openDb` makes any that a database lacks, after the migrations. The first time there were none (2026-10-10, at the owner's ask to clear his test types) it also moved every deck onto the default one, Wanikani+, through `updateDeck` so cards kept their rung, and hid every type from before. `removeSrsType` answers `"builtin"` for one of them and the route says 409; a `PATCH` to one is 409 too, they are view-only (`SrsTypeView` draws a read-only screen for `builtin`, `FlowCanvas` takes `readOnly`), and every time the database opens each one is brought up to what `srsStarters.ts` defines today (`makeStarter(starter, mint, as)` builds it under the existing row's stage and answer ids, position for position, and `updateSrsType` writes it; nothing is recorded when nothing differs). Changing a built-in type is therefore an edit to `srsStarters.ts`, never a migration, unless a stage with cards on it goes away. A new type is `copySrsType` of any type in the list, under fresh ids. **The SRS editor saves on purpose** (no autosave, no drafts; the owner tried a draft kept in `localStorage` on 2026-10-10 and had it removed the same day): `SrsTypeView` holds the edited type in state, sends nothing until Save (`PATCH`, or `POST` for a type never saved, which until then exists only in the `srsEdit` screen's own `type`, so a reload of its address lands on the list), and there is no Discard: leaving without saving drops the changes. Save is drawn by `App` in the header (`headFor`) and calls the guard's `save`; the editor reports `canSave` in its `SaveStatus`. The question on leaving is `Modal`, the app's one pop-up. **Leaving unsaved work asks first**: while it's dirty the editor hands `App` an `UnsavedGuard` (`onGuard`: its name and a `save` that says whether it went through); `go` sets `leaving` instead of going, a `popstate` puts the editor's address back and sets `leaving` too, and the question's three answers are Stay, Discard changes (`go(next, true)`) and Save and leave. A reload or a closed tab is covered by `beforeunload`, the browser's own question. A type's `description` is a column on `srs_types` (default empty, so older rows and requests read as none). **A stage's own rules that equal the default are dropped**: every change in `srsFlow.ts` goes through `edit`, which ends with `settle` (an override that does the same as the default for every answer is deleted), so "has its own rules" always means they differ. **`retry` is a step** that resolves to the same place with a wait of 0 (`again: true`): inside a right-away ask-again it loops a card in the review until another answer leaves the box. **"Back to the start" is no longer a step**: `upgradeFlow` in the contracts reads a stored one as "go to the first stage", run in `srsTypeFrom` before parsing (old data normalised on read). **An answer has `aside` and `confirm`** (optional in the contracts, two `INTEGER` columns on `srs_answers` from the latest migration): `mainAnswers` is the answers not set apart, which is what the preview, the forecast and the answers' colours (`answerClass`) go by; `ReviewView` draws the main ones in the row, the rest under it, and holds an answer that asks first in `asking` until the yes. **A stage can have no wait**: its `wait.n` is 0 (`StageWait` in the contracts allows it; an ask-again's wait stays 1 or more), stored in the same `wait_n` column, so no migration. **Only a wait of 0 comes back in the same review** (a right-away ask-again, or a stage with no wait): an ask-again with `now` resolves to a wait of 0, and `ReviewView` puts a card back in its queue only for that; anything with a wait is for a later review. **Hiding a stage with cards on it asks where they go**: the save carries `moves`, the API refuses it without them (`409`), and each card gets a `'stage-removed'` row. **Switching a deck's SRS type** maps each card by position (rung 3 stays rung 3; past the new top counts as the top) with a `'switch'` row each; a burned card stays burned. What a review shows (`dueCount`, `newCount`) is derived per deck with the API's clock and the settings: due = not burned and due by now plus the hours-ahead window; new = the deck's never-answered cards, as many as the day's count allows (new cards started in that deck since the day began come off the deck's own `newPerDay`; the deck's own `reviewsPerDay` caps the due ones; there is no limit across decks and no hours-ahead window any more, so a card is due exactly when its wait is up). The shared `Settings` are only `fuzz` and `dayStartHour`. **A deck's own settings** (`DeckSettings`: `newPerDay`, `newPlace`, `newOrder`, `reviewsPerDay`, `reviewOrder`, `againPlace`, `pool`; `againPlaceOf` is the place that really applies, always "soon" with a pool; a deck's `dueCount` is under both its own `reviewsPerDay`, counted from its answers that didn't start a new card, and the shared one) are a JSON column on `decks` holding only what the owner changed, read over `DEFAULT_DECK_SETTINGS` key by key (a stored value that no longer fits reads as the default), changed through `PATCH /decks/:id` with a `deck_settings_changes` row per key. The order of a review is the web's: `ReviewView` builds the day's line (`buildQueue`), keeps `pool` cards in play and the rest waiting (`startLine`), and after each answer `advance` puts a card with no wait back where `againPlace` says or lets the next waiting card in. "More new cards today" on the end screen is the web's too: it starts a fresh line from the deck's unstarted cards, past `newCount`; the API never refuses an answer for being over the day's count, it only stops offering new cards (`newCount` 0) until the day turns. The day begins at the settings' hour in `PANKI_TIME_ZONE`.

**A file on a card is a row and a file** (step 15). Three of a field's kinds hold a file instead of text (`audio`, `video`, `image`; the contracts' `mediaKindsOf(fieldKind)` says which, and the words are the same as `MediaKind`'s on purpose). The card's value in such a field is the file's id, kept in `card_values` like any value, so a card's history, its edits and its shape need nothing new. The file is sent first, on its own (`PUT /api/media/:id`, the raw bytes as the body), under an id its sender minted; the card that names it is made after. The API believes the file, not the request: the type in the header must be one Panki takes (`MEDIA_MIMES`: webm, mp4, ogg, mp3, m4a; jpeg, png, webp; nothing that can carry a script) **and** the file's own first bytes must agree (`mediaFiles.ts` → `sniffMimes`). A container says nothing of what's inside, so webm and mp4 pass for sound and picture alike, and the sender names one for the field it's going into (`mediaMimeFor`). Each kind has its own ceiling (`MEDIA_MAX_BYTES`: 10 MB a sound, 40 MB a clip, 5 MB a picture). The bytes are written under another name and moved onto their own, then the row is made, so a failed upload leaves nothing that claims a file is there; the same id with the same bytes again answers with the row, the same id with other bytes is refused (`409`), never overwritten. **A card can only name a file its own account holds, of its field's kind**: `cardProblems` checks the shape (an id), and the cards routes then look the file up, because only the API can know. Served only to a signed-in device of the account that holds it, by id, with the type from the row, `nosniff`, a year of `private, immutable` caching (a file never changes under its id) and byte ranges, which is how a clip is skipped through (`res.sendFile` with `root`, so only the id is ever a path). Nothing removes a file yet.

**Migrations** live in `db.ts` as an ordered list (`auth.sqlite` has its own, in `authDb.ts`); SQLite's `user_version` records how many have run, each runs once inside a transaction. Migration 13 (media) added the `media` table, empty: nothing from before is touched. Migration 14 (sources) added `card_sources`, empty too. Migration 15 (deleting a card) added `cards.removed_at`, NULL for every card from before. Migration 11 (the silo) added `review_sessions`, `events`, and the `session_id`, `think_ms`, `decide_ms` and `miss` columns on `card_places`; answers from before read as NULL in all four, so the stats count them as neither right nor a miss. Migration 12 (card edits) added `card_value_changes`, empty: nothing from before is touched. Migration 2 (decks) moved any cards that existed before decks into one deck named "Default" — a placeholder, not a name the code knows. Migration 4 (card types) made the starter type "Word" (Word front required, Reading back, Meaning back required), gave it to every deck, copied each card's three columns into `card_values`, and then dropped the columns: the text moved, nothing was lost. Migration 5 (field kinds) added `kind` to `card_fields` with `'text'` as its default: every field from before holds one line, nothing else changed. Migration 6 (the SRS) made the three starter SRS types from the contracts' `makeStarter` (WaniKani-like, Classic, Gentle, a millisecond apart so they list in that order) and put every deck on the first; every card from before is new to it. The starters gained their start stage (Lesson / New, no wait) after that migration ran on the owner's data, so their three types have the old first stage (Apprentice 1, 4 h) first, and since 2026-10-10 it waits its 4 h like any stage; the starters' ten-minute first stage is only in types made after that. `deck_id`, `type_id` and `srs_type_id` are nullable at the SQL level only because SQLite can't add a `NOT NULL` column without a default; the API always sets them.

## API surface

All JSON, but for a file's own bytes (the two `/api/media` routes). Validation at the boundary with the shared Zod schemas; a failed parse is `400 { error: { message, path } }`. Unknown `/api/*` is `404`. Errors never leak internals. Every read that derives a count or a due time takes the API's `now`.

**Everything under `/api` but `POST /api/login` needs a live session**, the app's cookie or the extension's `Authorization: Bearer …`, else `401 { error: { message: "Sign in to continue." } }` (a cookie that names no live session is cleared as it's refused). `session.ts` → `requireSession` looks the cookie's hash up, touches `last_seen_at` at most once a minute, and puts who it is on `res.locals` (`signedIn(res)`, with `admin`); every router takes `dbOf(res)` and reads that account's own database (`app.ts` → `DbOf`), so one account never sees another's rows. **What everyone shares is read by anyone and changed by an admin alone:** the routes marked *admin* below go through `requireAdmin` as well, `403 { error: { message: "Only an admin can change this." } }` for anyone else.

| `POST /api/decks/:deckId/sessions` | `NewReviewSession` (`id`, `kind`) | `201 { session: ReviewSession }`, stamped with the API's time and the signed-in device; the same `id` again returns the sitting as it is |

## Frontend architecture

**Every screen has an address** (the owner's ask, 2026-10-10, so the browser's back and forward and a mouse's side buttons walk the app): `routes.ts` is a screen by ids alone (`Route`), written as a path (`routePath`: `/decks`, `/decks/:id`, `/decks/:id/settings`, `/decks/:id/review`, `/review`, `/review/:id`, `/add`, `/types`, `/types/new`, `/types/:id`, `/types/:id/layout`, `/srs`, `/srs/new`, `/srs/:id`, `/settings`) and read back (`parsePath`). `go` pushes a history entry; a `popstate` or a reload sets `arriving`, and `App` turns it into its `Screen` (`screenOf`) once the list it names is loaded, landing on the list when the thing is gone. No router library. Whatever serves the built app must answer any of those paths with `index.html` (Vite's dev server does). No store: `App` holds where you are (`Screen`: home, decks, a deck, the review picker, a review and where it came from, add, the card types, one type or a new one, the SRS types, a new one, one being edited, settings), the decks, the card types, the SRS types and the settings, the open deck's cards, whether the new-deck or add-card form is open, which deck the Add screen last used, and what the SRS editor's header says; props down, callbacks up. Every screen that shows a card looks the deck's card type up in the loaded types and hands it down: `CardForm` draws one `TextField` per field (a box of several lines when the field's kind says so), `CardList` and `ReviewView` put the Front fields first (the first one big) and the Back ones after the flip, a Paragraph keeping its line breaks. What each kind is (its word, one line or many) is the `FIELD_KINDS` registry in `fieldKinds.ts`; the ids are the contracts' `FieldKind`, so the API refuses a kind that doesn't exist. Japanese text gets `lang="ja"` by looking at the text (`words.ts`), never by a setting. The fixed places in the bar are the `TABS` list; what each screen's header shows (back and where it goes, the title, the action) is `headFor`. `api.ts` is the only place that calls `fetch`, and it parses every response through the contracts. Adding waits for the API's answer, then puts the saved row into the list (optimistic UI comes when it's worth it). The decks, the types and the settings are fetched again whenever the screen changes (and after a card is added), because their counts are derived on the server; the open deck's cards are fetched when the deck changes and kept from a deck to its review, and a deck is read from the list by id so its counts move with every answer.

**Room on the disk (2026-10-11, at the owner's ask: "so I don't have to check manually and worry about it").** Clips are what fill a small VPS. `apps/api/src/space.ts` is the one place that measures: `diskOf` asks the disk under the data folder what's left (`fs.statfsSync`, asked every time, never remembered, since other things fill the disk too), `spaceOf` adds `low` (less than `env.lowSpaceBytes` left: 2 GB unless `PANKI_LOW_SPACE_MB` says otherwise, one home in `env.ts`), `accountSpace` weighs an account's folder and reads its files by kind from its own `media` table. That read opens the account's database **for reading only** (`readOnly: true`), so the command runs no migration and changes nothing under a server that has the same file open. `pnpm space` (`cli/space.ts`) prints it; `createApp` takes `space` as it takes the clock, and `GET /api/space` hands it to whoever is signed in. The web asks with the home's stats and draws `SpaceNotice` above the board while `low`; a failed ask is silent, because a warning that can't be had must never take the home down. Sizes are phrased by the contracts' `sizeWords`, for the terminal and the app alike. **Not built:** refusing an upload when the disk is nearly gone. Today a full disk fails the write and the API answers 500.

**Media: one kind of field for a clip or a sound (2026-10-11, the owner: "remove the type video and audio, replace it with simply media which can be either").** `FieldKind` is `text | long | media | image | youtube`. What files a kind takes has one home, `type.ts` → `mediaKindsOf(kind)` (`media` → video or audio, `image` → image), with `holdsFile(kind)` for the yes or no; the old one-to-one `mediaKindOf` is gone. A file's own kind (`MediaKind`: audio, video, image) is unchanged and is what the `media` table has always kept. **Migration 16** is one statement, `UPDATE card_fields SET kind = 'media' WHERE kind IN ('audio', 'video')`: no card and no file is touched. Since a field no longer says which of the two its file is, **the card does**: `Card.files` (file id → `MediaKind`) is derived on every read, from the `media` row each value names (`db.ts` → `valuesWithMedia`, a left join; `cardsFrom`). The web draws by it (`fieldKinds.ts` → `fileKindOf(kind, value, files)`), so a clip gets its frame at once instead of after its file has loaded; an id with no file behind it is left out rather than shown as words. A file picked by hand is told apart by the contracts' `mediaFor(kinds, type, name)`: what the browser calls it first (a `.webm` it calls sound goes in as sound), then the field's kinds in order; `MediaField` takes `kinds` (what the chooser offers) and `kind` (what's showing). The API accepts a file in a field when its kind is one the field takes. The extension records into such a field as video or as sound, whichever the piece mapped to it is (Sentence video, Sentence audio, Word video, Word audio).

**A card's layout (2026-10-15, the owner's pick of four ways: B, edited on the card itself; https://claude.ai/artifact/DWyM6RaC2xMtSrBMbuxCyf; built, not yet seen).** A card type carries a `layout`: one part per field, in the card's own order (`contracts/layout.ts` → `LayoutPart`): what the front and the back each do with it (`FaceShow`: show, spoiler, hide), its size and colour (words; a picture's or a clip's size too), whether its name shows, a sound or a clip as the player or a button (`MediaLook`), whether it plays by itself, whether it sits beside the one above, and (`over`, 2026-10-16) the field whose words it's written over, as their reading. **It's derived, never trusted as kept:** `cardLayout.ts` → `layoutOf(fields, kept)` reads what's kept part by part (a broken bit reads as the field's default, a part for a field the type no longer has is dropped, a field added since joins at the end), and when nothing would show on the front the first part does. **A type nobody laid out looks as it always did** (`defaultLayout`): its front fields first, the first of them that holds words big and the rest quieter, then its back fields, which hold their room on the front, unseen. So every existing card looks the same until its layout is changed. **A field's side is now the layout's**: `typeFrom` sets each field's `side` from its part (`sideOf`: the front when the front shows it at all), and saving a layout writes the sides with it; what knows only two sides (a deck's card rows, a form's big field, the API's name for a card) keeps reading `side`. The Fields tab has no side control any more, and the old "a card needs a Front field" rule moved into the layout ("Put something on the front."). (`layout.ts` holds the shapes and imports nothing of `type.ts`, which takes `CardLayout` for its `CardType`; the functions that need a field's kind are `cardLayout.ts`, so the two never load each other.)

- **Drawn by the one card** (`components/ReviewCard.tsx`). Each part is drawn where the layout puts it, on the side showing; rows are parts set beside the one above; runs of rows whose parts only ever show once the card is turned are one `.review-answer`, unseen on the front but holding their room, so turning moves nothing (a lone part like that in a mixed row is `.is-later`). A spoiler is the app's `Button variant="spoiler"` over the part, a plain block of its shape with no word on it (as Discord hides a message; the owner had the word "Spoiler" taken off it, 2026-10-15), its content `inert` and unseen under it; pressed, it's open until the card goes back to its front (`opened`), so a spoiler opened on the front stays open when the card is turned. **Playing by itself** (`autoplay`, which only the review passes): the parts in view whose `auto` is on and whose value is a sound or a clip are cued one after another in the card's order (`cued`, `played`; `MediaView` takes `cue` and tells `onCueEnd` when it ends, is stopped, or can't start), each once while the card shows, a spoiler's when it's opened; turning the card plays what newly came into view. The review keys the card by its id, so nothing carries over to the next card. **A reading over a word** (`over`, set on the reading by its "Reading above"): the reading is drawn as the named field's `<ruby>` (`readingFor`, `readingOver`) wherever the two stand in the card's order, with no place of its own then; its Size, Field name and Position are disabled (they're the word's to say), its Colour colours the `rt`. The ruby stands on a line of its own with the reading's room above it (`.review-ruby-line`), so a field name over the word stays clear, and its words are one box (`.review-ruby-text`) the same size covered or open, so opening a spoiler moves nothing (the owner, 2026-10-16, saw it jump, the cover being a block taller than the words); on the card being laid out a spoiler reading is covered as any part is there, its words faint. Both must be on the side shown and Text; one reading over one word, and a reading never has one of its own (a claim that doesn't hold leaves the part where it stands). Held for the back its `rt` is `.is-later`; a spoiler's words stay in the `rt` unseen with a `Button variant="spoiler"` laid exactly over them (`.review-ruby-covered`, the button `position: absolute; inset: 0`): a button in the line is a box of its own, taller than the words, and made the card grow until it was opened. While the card is laid out it's drawn the same, the word's body left un-`inert` so the `rt` (`.review-ruby-pick`) is pressed to pick the reading, its name standing in while the card leaves it empty. `layoutOf` keeps an `over` only when it names another Text field of the type and the part is Text too. (Two tries came first the same day: a boolean `over` for "the one below", and `reading` on the word; both are read as nothing now.)
- **What a file is, told apart.** `MediaView` draws a sound and a clip each in its own colour (`--sound`, `--clip` in `theme.css`, made of tokens every theme sets) and, when its part's name is on, the kind's icon (`MEDIA_ICON`: sound, film, picture) and the name on it.
- **Seven player styles for a sound or a clip** (2026-10-15: the owner, shown four new ones on https://claude.ai/artifact/2WEFUoj7rsgbJUp3KQB8yi, had them all built to choose from per field, and the browser's own kept as `plain` after trying it in place of Panki's player: "I liked the old player more"). **Full screen** is the player's own: a button at its bar's end (and a double-click on the picture) puts the player's frame, picture and bar together, into full screen (`requestFullscreen` on the frame; whether it's full is read off the frame's own root, a shadow root on someone else's page, so the extension's drawer behaves too), on `--theater` black. `MediaLook` is `player` (the bar, a clip's picture over it), `button` (the row's chip), `voice`, `round`, `tile`, `speaker`; the four new ones are `components/MediaLooks.tsx` and play a clip's sound alone through an `<audio>`. Every look plays through `hooks/usePlayback.ts` (lifted out of the player), so cueing, stopping and failing are one thing. The voice note's waveform is the file's own: `waveform.ts` → `waveOf` reads the bytes (`api.fileBytes`, still the only place that calls `fetch`), decodes them in an `OfflineAudioContext`, and takes the loudest sample of each of 36 stretches against the loudest of all; a file it can't read or decode stays level, never a made-up shape; what's read is kept for 80 files while the app is open. Only the review and the Layout tab hand `ReviewCard` a `waveOf`; the extension's drawer doesn't, so no page's script ever reads a file (its built scripts were checked: no `fetch`, no `decodeAudioData`). A press on the waveform goes there (`seek`); how fast it plays is the app's `Dropdown` at its end (0.5×, 0.75× or 1×, never faster, 1× to begin with, lit while it isn't; the owner had a lone 0.75× button made a dropdown: "that's lazy"), keeping the voice's pitch. Only the player and the voice note stretch across a row or take a size; the round button, the tile and the speaker keep their own width, and a speaker set beside the words above sits right after them.
- **The editor** (`views/LayoutView.tsx`, the Layout tab of a card type, `/types/:id/layout`). The card is `ReviewCard` with `edit` (`CardEdit`): every part on the side shown is picked by a press and moved by the grip at its left (`useDragOrder` over the side's parts, `partsOn`; one order with the list's, `movePart`), its content `inert` so a press on a player picks it; a field the card shown leaves empty stands as its name. The parts not on the side shown are chips under the card. The picked part's choices are `Setting` rows (its two sides; then its player style, size, colour, name, plays by itself, beside the one above, as its kind allows; no line under any of them, the owner found them "self explanatory"), beside the card on a wide screen and under it otherwise (a list of every field under it all was taken out the same day at the owner's word, "useless"; the name's switch reads "Field name: Shown / Hidden", their wording for something a SaaS would say). **The card shown is one of the type's own** (the newest of up to 30 from every deck on the type, `api.listCards`; or each field's name), with its deck's ladder for the pill. **Edit / Preview** (a `Segmented` pair: it was a switch, "Try it", then "Preview", until switches had to say their state) makes the card a review card for a moment: on its front as it starts, pressed to turn and back, spoilers to open, autoplay on; the Front / Back choice is off (`disabled`) until Edit. Saved by the header's Save (`App` → `saveAction`, the same as the SRS editor's; `editStatus` is whichever editor is on screen), leaving unsaved asks first, and Ctrl+Z undoes (`hooks/useUndoable.ts`, lifted out of the SRS editor so both are one history). Saving sends the type's fields as they are with the layout (`App` → `saveLayout`).
- **Unproven, never run:** the layout editor and the new card in any browser (drawn from the code alone); `inert` letting a press through to the part under it (Chrome and Firefox both have it); playing by itself without a press first on a phone (the review has had presses, so it should be allowed; a refusal only skips it); dragging parts that sit side by side (the list's drag was made for a column: they move, but the others slide up and down rather than aside).

**A field that holds a link (the YouTube link kind, 2026-10-11).** The kind `youtube` is a field whose value is a video's address, kept as it was given. `packages/contracts/src/youtube.ts` is the one reader and writer: `youtubeLinkOf(text)` takes an address apart into `{ videoId, seconds }` (a watch page, `youtu.be`, a short, a live one, an embedded one; `t=83`, `t=1m23s`, `start=83`; null for anything else, and for an address with words around it), and `youtubeUrl(link)` writes the one address Panki ever opens, `https://www.youtube.com/watch?v=…&t=…s`. It reads with patterns, not `URL`, because the contracts are built with neither the browser's nor Node's globals. `type.ts` says what a kind holds: `mediaKindsOf` (a file), `holdsLink` and `linkOf(kind, value)` (a link), `holdsWords` (neither: what a card is called by and what's shown big; the stats' toughest cards, the form's delete question, the list and the review card all ask it). `cardProblems` gives `link` for a value in such a field that isn't one, so the form says it and the API refuses it; as with a file, words left in a field from before it held links are no fault of a change that leaves them alone (`firstProblem` in the API, `leftAlone` in `CardForm`), and they are still shown as words. **What's shown is never the stored value as an address:** `LinkView` draws an `<a>` (the app's only one, dressed as a chip: `.link-chip`) whose `href` is `youtubeUrl` of what was read, `target="_blank" rel="noopener noreferrer"`, so nothing typed into a card can become a link that runs a script or goes anywhere but YouTube. It stops its own press, as a player does, so the review card under it isn't flipped. No player of YouTube's is embedded and nothing is fetched from it: that would be a remote service, which is the owner's call to make. No migration: `card_fields.kind` has no CHECK.

**Media in the web (step 15).** A field's kind decides what it's filled with: `mediaKindsOf(field.kind)` from the contracts is the one question the form, the list and the review card ask. `CardForm` draws a `MediaField` for a field of files and holds what was picked as `{ id, file, mime }` (the id minted the moment it's picked, the type from `mediaMimeFor`, a file Panki doesn't take or one over its ceiling refused there and then, under the field), so the card's values can be weighed by `cardProblems` before anything is sent; on Add the files go first, one `PUT` each, and only then the card, so a card never names a file Panki doesn't hold, and a failed upload is said under its own field with no card made. A retry sends the same ids, which the API answers as already there. `MediaView` is the one way a file is shown: an `<img>`, or an `<audio>` / `<video>` with no controls of the browser's and the app's own bar (play, a line of progress from `timeupdate`, the time), `preload="metadata"` on a card and `preload="none"` on a row, where a sound or a clip is a chip that plays the sound only, so a long list fetches nothing until pressed. Nothing plays by itself. A file's address is `api.mediaUrl(id)`; the element fetches it with the sign-in cookie, and the API's byte ranges do the seeking. A clip recorded in a browser often carries no length, so the bar then shows the time so far and fills only at the end. On the review card a press on the player is the player's (it stops there), so it doesn't flip the card; Space still flips, as everywhere. `fileKindOf(kind, value)` in `fieldKinds.ts` is what decides a value is shown as a file: its field holds files **and** the value is an id, so words typed into a field before its kind was changed are still shown as words. The big word on a row and on the review card is the first Front field that holds text, and the API's "toughest cards" reads the same field.

**Changing and deleting a card (step 18).** In a deck's Cards view each row ends with an edit button (`CardList`'s `onEdit`; always drawn, never hover-only), and the card that's open is drawn as its form in the row's own place in the list (`editing`), which `CardsView` holds as one id. The form is `CardForm` again, given a `card`: it starts from the card's values (`startFrom`: words into the text fields, file ids into the fields of files, where `MediaField` shows the held file from `api.mediaUrl`), and on Save sends **only what differs** (`changedFrom`), so nothing untouched gets a row in `card_value_changes`; a new file goes up first, as when adding. Words still sitting in a field from before it held files are neither shown as a file nor cleared by a save that leaves the field alone, and the API no longer faults such a leftover on a change that doesn't touch it. Delete is in the same form: Delete… turns the form's foot into the question with what it costs, Keep beside the filled Delete card, the panel in its alarm colours (`DeckSettingsView`'s pattern). Two `CardForm`s can be on one screen now (the add form above the list, a card open in it), so each names its fields with its own `useId`. `App` keeps the open deck's cards: a save swaps the card in, a delete drops it and reloads the lists for the counts.

**The SRS in the web.** The words and looks are one registry, `srsKinds.ts` (the units, the steps a rule can be, how a stage, a place and a wait are phrased, a stage's colour from its place on the ladder); the rules in the contracts (`resolve`, `dueAt`, `waitNow`) are what the API runs, so the review's buttons say exactly where the API will send the card. `srsFlow.ts` edits a type without touching the one in state (every change returns a new type: set a step, wrap a step in an ask-again or flatten it, add or remove an answer or a stage with its rules cleaned up); `srsPreview.ts` walks a card through a type for the preview. **The editor (`SrsTypeView`) keeps a history** (past, present, future; a run of keystrokes in one field undoes as one) and **saves on its own** half a second after the last change, when the type parses; a change during a save queues the next; the header shows Saved / Saving… / Not saved yet (with the field's error under it) / Not saved. Hiding a stage with cards on it opens the question in the Stages panel and the next save carries the move. **The chart (`FlowCanvas`)** lays the rules out as a tree (one column per ask-again deep, one row per outcome, the stage or the default rules at the root), draws the arrows as SVG and the boxes as buttons on one sheet. **The sheet is laid out at the zoom (CSS `zoom`) and panned by whole pixels, not stretched with `scale()`**: a stretched layer drew blurred text and stray lines at the boxes' corners in Firefox, the owner's browser, at zooms like 96%; only under `G.sharpMin`, where browsers stop shrinking text, is the rest of the way a stretch. An icon inside a box is an svg too, so the arrows' sheet is styled as `.sheet > svg`, never every svg in it. An arrow runs from its answer's port through the answer's name to the box; pointer events on the frame pan it or drag a box or an answer's name (a name is kept as its distance from its port, so it follows its box; pointer capture, a 4px slack before a press becomes a drag, the click after a drag is swallowed), a native non-passive wheel listener zooms around the pointer (the ground is dragged to pan) and, over the rail, moves the stages sideways, the menu beside the picked box is placed from the box's geometry and clamped into the frame in a layout effect and closes on its ×, on a press on the ground that never became a pan, or on Escape. The boxes have no hover hints (removed at the owner's ask, 2026-10-10). **An ask-again can be capped** (`capped` on the step, optional so older rules read as not capped): `againWait` in the contracts gives the shorter of its own wait and the stage's (the card's current stage, never the next), and `resolve` and `waitNow` both go through it, so the API, the review's buttons, the preview and the chart all agree; starters and a newly added ask-again are capped. Box positions the owner dragged and the view live in the canvas's state per scope, and each scope is fitted to the frame the first time it shows. **The review (`ReviewView`)** builds its queue once from the cards' `due` and `dueAt` and the deck's `dueCount` / `newCount` (soonest due first, new ones as added or shuffled, in the order the Settings say), answers through the API, and a card that comes back within the hour is put back at the end of the queue. **Settings** saves each change a moment after it's made, a few quick ones as one.

**The frame is one CSS grid** in `app.css`, with named areas: on a PC the brand and the tabs share the top bar and the screen's own header sits in the 640px column; under the phone breakpoint the tabs become a bottom bar (sticky, above the safe area) and the screen's header becomes the top bar, the brand showing only on Home. One DOM, two placements. The SRS editor is the one screen that widens the column (`is-wide`, 1140px) and, at its own breakpoint, puts the preview beside it. While a field in the main column has focus the bottom bar is hidden (`:has`), because the keyboard is taking the room; what sticks to the bottom of the review sits above the bar by its height (`--tabbar`).

Fonts are self-hosted under `apps/web/public/fonts/` (Urbanist, two Latin subsets, OFL) and declared in `theme.css`; Japanese text uses the device's own fonts because CJK files are too large to ship. Nothing is fetched from a font CDN.

The mark (パ) lives as outlines in `src/brand/geometry.ts`, taken from Noto Sans JP at weight 900 so it is the same glyph on every device. `brand/Mark.tsx` draws it as four stacked SVG layers (the tile, the two strokes, the ring) so a moment can move each part; `pnpm icons` renders the same geometry into `public/icon.svg` and the PNGs the tab and the manifest use, with the colours read from the `--mark-*` tokens (the same in both schemes). **Animation is CSS keyframes, no library.** `components/Intro.tsx` mounts an overlay once per page load; its whole timeline sits in `app.css` next to the keyframes; it ends on the overlay's own `animationend` (a 3-second timer is the fallback) and never plays under `prefers-reduced-motion`. A library comes in only when a sequence can't be said in CSS.

**On a page that isn't Panki's.** `ui/mount.ts` makes an element with a **closed shadow root**: the page's scripts can't read into it, the page's styles don't reach in, the app's don't leak out. **Reading the line (`capture/captions.ts`).** Nothing is fetched and nothing of the player's is called: a `MutationObserver` on the player's caption area reads the words already drawn, and stamps each line with the video's own time as it appears and as it goes. The last few lines are kept (`KEEP`), in the video's order; a line seen again where it was (a rewind, a clip played back, the replay that records it) is the same line, not a new one, and keeps the end it had; a line cut off by a jump ends where the video was, not where it landed. **Seen again means two things** (`read`): the whole of its text about where it was, or only the beginning of it inside its own time, because the player writes a row of its own captions out a word at a time every time round. Without the second, each time a clip was played back its lines were taken for new ones, and since only the nearest few are kept they would in the end have pushed out the very lines being added. `writing()` says which line is on screen being written right now, for the first time or again. A line is **heard out** when the captions moved on from it, and only **cut short** when the video jumped away part-way: both have an end, but a cut one's is just where the video was, so while it's being written again `unfinished()` names it and a sentence that runs to its end waits for it, exactly as for a line written for the first time. **A caption shown whole is one line; the site's own listening captions roll up a row at a time and are written a word at a time, and there each row is a line**: the bottom row is the one being written, each stretch it gains is stamped with its time (`marks`), and the rows above it are matched back to the lines they were (`shown()` is what's on screen, top to bottom, or what was last there). **Under the player Panki has two rows of its own, each the whole width** (`youtube.tsx` → `rowsUnder`, `Row`). The player's rows are short, made for the middle of a video, so each of Panki's holds several of them end to end: how many (`perRow`) is the room measured off the rows themselves (a `ResizeObserver`, in full-width characters) divided by the longest row the player has written in this video (`longestRow`, which only grows). **A line's row is fixed by its place in its stretch of talk** (`Line.run`, `Line.seq`, given once in `captions.ts` → `add`; a silence longer than `NEAR` starts a new run at 0), so words never move sideways once drawn: a row fills from the left, and when it's full it moves up whole (keyed by run and row) and the next begins, the way the player's own captions roll, only wider. Exactly two rows' height is always kept and a lone row sits on the lower one; a row never wraps (what it holds is counted to fit, and the overflow is cut sooner than a third row is made), except in a window too narrow for even one of the player's rows. Nothing later than the line being written is drawn, so going back over a video doesn't show what's still to come. Its time comes from the marks (`timeOf` where its first words appeared, `timeAfter` where the words after it did), so a clip covers the sentence and not the rows it happened to be drawn on. A sentence that runs to the end of what's shown is let finish: the video stops when the bottom row is over (and is started, if it was stopped by hand part-way through it, so its clip has an end). The class names are the site's and are gathered at the top of `captions.ts` and `youtube.tsx`: **they are the first place to look when the line stops showing.** The line is split into words by the dictionary when there is one (step 19, below), and by the browser's `Intl.Segmenter` otherwise (`capture/words.ts`), which splits finer than a dictionary would, so a pick can be widened to the piece beside it. Each word is drawn in a box of its own (an inset shadow, not a border, so a re-split moves nothing after it by more than a hair; `ROOM_USED` counts the boxes' room).

## Implementation lore

These are the traps that cost real time. Each is load-bearing — re-solve before removing.

- **The shape library tries to run made-up code the moment its first shape is made** (Zod's fast path probes `new Function`). In an extension that's refused, and the refusal is listed as an error against the extension, or reported against the page a script stands on. `z.config({ jitless: true })` only helps if it runs before any shape exists, and the contracts make theirs as they're imported: `apps/extension/src/setup.ts` is therefore the first import of every entry, and the built files were checked for it coming before the first contract shape.
- **A script built as one file gets no `process.env.NODE_ENV`.** Vite's library mode leaves it for whoever consumes the library; React then asks a browser for `process` and the script dies on its first line. `build.mjs` defines it.
- **From outside a shadow root, an event's target is the root's host.** The web's `Dropdown` closed on every press inside itself when put in one, until it looked at the press's path (`composedPath()`) instead of its target.
- **`crypto.randomUUID` only exists on a secure page.** A page's script runs on http pages too; the extension's ids come from `uuid.ts`, made of `getRandomValues`.
- **A message between an extension's parts carries JSON, not bytes** (in Chrome). The clip goes to the worker as base64 and is turned back there.
- **A file read as a data address is cut at its last comma, never its first.** A recording's type is `video/webm;codecs=vp9,opus`, comma and all, and it stands before the text. Cutting at the first comma sent the worker `opus;base64,…`, which isn't base64: the owner's first clip (2026-10-11) died there with "Something went wrong" while its card was added fine.
- **A button that paints no background of its own is grey.** The browser's default `buttonface` fill showed on the tab and chip variants in the screenshots and in no check. `.btn` sets `background: transparent`; each variant paints its own.
- **A box of several lines grows with `field-sizing: content`,** which Chrome has and others don't: `rows=3` is the floor and the fallback, and `resize: none` keeps the browser's grip off it. The phone's bottom bar hides while an `input` *or* a `textarea` has focus (`:has(:is(input, textarea):focus)`), or the keyboard squeezes it.
- **A dispatched click lands only inside the window.** Headless Chrome drops an `Input.dispatchMouseEvent` whose point is off screen; once the type editor outgrew the 900px window, Save was never pressed and the check timed out with nothing to show. `rect()` in `verify.mjs` scrolls the element into view before measuring it.
- **Reordering is pointer events, not HTML5 drag and drop.** Android Chrome starts no native drag from a touch, so one pointer-event implementation (`useDragOrder`) serves mouse and finger; `touch-action: none` on the grip keeps the page from scrolling instead, and the grip takes pointer capture so the row keeps following a finger that strays. A row moved by key loses its focused grip (the DOM node moves), so the hook refocuses it.
- **A tap right after a touch gesture is swallowed.** Chrome drops the click of a tap that lands within about a second of a touch drag's end (its guard against accidental taps): the pointer events fire, no `click` follows, and nothing says why. `dragRow` in `verify.mjs` waits a second and a half after a finger drag; a real finger is never that quick.
- **React's `onWheel` can't stop the page scrolling.** React registers wheel as a passive listener, so `preventDefault()` in it is ignored and the page scrolls along with the chart. `FlowCanvas` adds its own `wheel` listener with `{ passive: false }` to the frame.
- **What a carried tile is over is read from where the tiles lay when the drag began, never from where they are now.** The board redraws itself under the pointer as a tile is carried; ask the page what's under the pointer (`elementFromPoint`) and the answer is the tile's own landing place, which reads as "over nothing", which puts the other tile back under the pointer, and the two trade places for ever. `useGridDrag` measures every slot once, on the lift, in page coordinates so a scroll doesn't shift them.
- **What a body reader's callback throws is nobody's.** Express catches what a handler throws while Express is the one calling it; a function run later, from inside `express.raw`'s own callback when the body has arrived, is called by the stream, and a throw there (a full disk as the file is written) would take the process down. The upload is therefore two handlers in a row (`routes/media.ts`): the first only picks the reader for the file's kind and hands on, the second, called by the router, does the work.
- **A file sent by `res.sendFile` needs `root`.** Without it every part of the absolute path is checked for a leading dot and a data folder under something like `.local` answers `404` for every file; with `root`, only the id after it is looked at. And a callback given to it must stay quiet once the headers are out: a browser skipping through a clip drops the request part-way, which arrives as an error with nothing left to answer.
- **A hoisted function doesn't keep a narrowing.** `const sel = selected; if (!sel) return; function onKey() { sel.split… }` fails to typecheck: a function declaration is hoisted above the guard, so `sel` is still `string | null` inside it. An arrow assigned after the guard keeps the narrowing.
- **The owner's watch-mode API reloads a migration the moment it lands.** `tsx watch` on 3001 restarted when migration 6 was written and ran it on the owner's live data; in the minutes between the contracts change (decks now carry `srsTypeId`) and the API's catching up, their running API couldn't parse its own decks. The migration was proven on a scratch copy of the version-5 schema first and the API files landed in one copy, so nothing was lost — but it is the trap `CONVENTIONS.md` warns of, and the next schema step should land contracts and API in one move or with the owner's servers stopped.
- **Windows can't tell `Mark.tsx` from `mark.ts`.** TypeScript resolved `./Mark` to the lowercase file and failed with "differs only in casing". Two files in one folder never share a name up to case; that is why the geometry module is `geometry.ts`.
- **Chrome on a phone paints its own blue tap highlight over whatever was tapped.** On the card-sized review surface it filled the whole card and looked like a broken theme; the checks all passed and only the screenshot showed it. `-webkit-tap-highlight-color: transparent` is set on everything in `app.css`, and pressed feedback is the app's own `:active` style. `pnpm verify` asserts the card's computed value stays transparent.

## Security architecture

The owner self-hosts on a VPS shared with other services, so **containment is the priority** and the realistic risk is supply chain, not app logic.

- **Zero outbound network calls.** No CDN, remote fonts, telemetry. The exceptions are the owner's own decisions, one host each, called by the API alone with the owner's key: Forvo, `https://*.forvo.com` only, for word audio recorded by people (2026-10-15, "Word audio from Forvo", above); and ElevenLabs, `https://api.elevenlabs.io` only, for a video's transcript (2026-10-17, "Transcribing a video", above), the one generated thing Panki makes, named as Panki's wherever it shows. The extension and the web still call nothing but Panki.
- **The API binds `127.0.0.1` only.** Nothing reaches it except through a proxy in front of it (nginx, once deployed). The sign-in (above, under "Data model": a cookie whose secret the database never holds, scrypt passwords, a throttle, one database per account) is defence in depth on top of that.
- **Validate every input at the trust boundary** with the shared schema; body size capped at 64 KB. The one route that takes more is a file's upload, read by its own reader under its kind's ceiling (40 MB at most), held to an allow-list of types that a browser plays or draws and that can't carry a script, and believed only as far as its own first bytes; what's stored is served back under the type from its row with `nosniff`, never under a name or a type the sender chose freely.
- **No hard-coded secrets; never log credentials.**
- **The extension is held to the same.** It calls one address, the owner's Panki; it asks the browser for the least it can (one site by itself, the acted-on tab otherwise); a page's script holds no secret and calls no network; what it draws on a page is sealed from that page. Its code is written here, none of it taken from another tool's (`CONVENTIONS.md` → Dependencies).
- Run non-root, unpublished DB, resource-limited, no host mounts once deployed.

## The owner's machine

- **`localhost` is slow on Windows:** Node tries IPv6 first, times out, then falls back — about a second per proxied request. Bind to and target `127.0.0.1` explicitly, everywhere.
- **Git Bash `sed` / `awk` can flip a file's CRLF/LF.** Keep each file's line endings consistent.

## Traps carried over from the Board (a web app)

Each is load-bearing — re-solve before removing.

**State.** Optimistic UI with the server as the authority. Anything another device must agree on goes to the server; "how this screen looks right now" can stay on the device. No global store until it's needed. When a stored shape changes, old data is normalised on read, never rewritten. Register `/things/reorder` before `/things/:id`.

**Phones and touch.** Nothing may make the page wider than the screen (check `scrollWidth` against `innerWidth` after adding chrome). `(hover: none)` — nothing points; a control hidden with `opacity: 0` still takes a tap. `(pointer: coarse)` — give small targets room with an invisible `::before`; every text field is 16px or iOS zooms. `100dvh` with `100vh` first; the viewport meta's `interactive-widget=resizes-content`. One phone breakpoint, in one place (`app.css`, 640px).

**Themes.** Every chrome colour is a token; a theme is one block that gives the tokens other values. Text on a filled, text-coloured button uses the surface token, never `#fff`. Something pale in every theme sets its own text colour. No flash on load once themes are switchable: an inline script in `index.html` sets `data-theme` before first paint. Native fields need `:where(input, textarea, select) { background-color; color }` from the tokens.

**The browser's own, replaced.** The tooltip is CSS-only. The form is `<Form noValidate>`: on submit it finds the first failing field, focuses it, and says what's wrong in the app's bubble under it. Panels open in the top layer, anchored to what opened them. A field's `autoFocus` is lost if its panel is still `display: none` as it mounts.

**Animation.** Move an element by animating transform from a static anchor, never `left`/`top`. An animation library's inline style beats your CSS — look at the screenshot.

**TypeScript.** `tsc --noEmit` on a "references shell" `tsconfig.json` (`"files": []`) checks nothing. Every package here typechecks its real config.
