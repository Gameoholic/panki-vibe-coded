# The web app

> **Scope of this file.** How the web app is wired: routing, state, keys, the card, the review and its fitting, and the traps in each. The pieces are `docs/COMPONENTS.md`; the screens as the owner sees them, `docs/PRODUCT.md`.

## Routing and state

- **Every screen has an address, with no router library.** `routes.ts` writes a screen by ids alone (`Route`) as a path (`routePath`) and reads one back (`parsePath`). `go` pushes a history entry; a `popstate` or a reload sets `arriving`, which `App` turns into its `Screen` (`screenOf`) once the list it names is loaded, landing on the list when the thing is gone. A card open in its deck's row replaces the address in place, so back still leaves the deck. Whatever serves the built app answers every path with `index.html`.
- **No store.** `App` holds where you are, the lists, the settings and the open deck's cards; props down, callbacks up. The lists are fetched again whenever the screen changes, because their counts are derived on the server; a deck is read from the list by id, so its counts move with every answer. Each screen's header is `headFor`.
- **`api.ts` is the only place that talks to the network** (`fetch`, and `sendBeacon` for the ledger), and it parses every answer through the contracts. Adding waits for the API, then puts the saved row in the list.
- **What each field kind is** (its word, one line or many, whether it holds a file or a link) is `fieldKinds.ts` → `FIELD_KINDS` over the contracts' `type.ts` (`mediaKindsOf`, `holdsFile`, `holdsLink`, `holdsWords`). Japanese text gets `lang="ja"` by looking at the text (`words.ts`), never a setting.
- **Every date and time is said by `words.ts`**, in the account's Time format and Date format (`Settings.timeFormat`, `dateFormat`): `App` hands them in with `setFormats` as the settings arrive, and `dateWords`, `dayWords`, `shortDayWords`, `fullDayWords`, `monthWords`, `monthYearWords`, `hourWords` and `hourOfDayWords` read them (the field order by `en-GB` / `en-US`, the hour cycle by hand, never a locale guessed from the browser). No other file builds an `Intl.DateTimeFormat` for something shown; the extension borrows the same functions and, never setting them, says them in the defaults.

## Unsaved work

A screen whose work takes a while to set up (a card type, its Layout tab, an SRS type, an AI action, an admin prompt) saves on purpose. It holds its draft in its own state with an undo history (`useUndoable`; Ctrl+Z), reports `SaveStatus` (`canSave`) to `App`, which draws Save in the header (`saveAction`), and, while dirty, hands `App` an `UnsavedGuard` (`onGuard`: its name and a `save` that says whether it went through). `go` then sets `leaving` instead of going, a `popstate` puts the screen's address back and sets `leaving` too, and `Modal` asks: Stay, Discard changes (`go(next, true)`), Save and leave. A reload or a closed tab gets the browser's `beforeunload`. A thing never saved exists only in its screen's state, so a reload of its address lands on the list. Settings and a deck's settings save each change a moment after it's made (`useSavedSoon`), a few quick ones as one.

## Signing in

`App` boots by calling `GET /api/me`; until it answers the frame is bare (`is-bare`: the brand, no tabs). **No answer at all isn't a sign-out** (a deploy restarting the API, nginx's `502`): the column says Panki can't be reached and asks again every `UNREACHED_RETRY_MS`. A `401`, from it or any later call, goes through `api.ts` → `onSignedOut`: `App` drops everything loaded, clears the unsaved-work guard, stops the ledger and shows `LoginView`, keeping the address so a sign-in lands where the owner was going.

## The ledger

`ledger.ts` queues events and sends them in batches; on `visibilitychange` to hidden and on `pagehide` it sends what's left by `sendBeacon`, since a fetch may not outlive the tab. It records nothing while signed out and drops its queue on a lost sign-in.

## Keys

`keys.ts` is the one home of every bind; `useHold` hears them.

- **A key is taken from another action only when both are the same shape of it** (a press, a hold or a double press, as its `holdMs` says): `clash`, the one check every way of setting a key goes through. The only actions that never take each other's key are those never heard together (`apart`: Show back of card and Step back, heard by precedence on their own side); Blur is heard on the front with Show back of card, so it clashes with it. A device whose keys were kept as `showCard` reads that key as Blur's, unless it clashes with Show back of card's.
- **Shift, Ctrl and Alt alone are keys,** heard only as their own press (`ownModifier`): decided as it goes up, and a hold lets go the moment another key goes down (Shift+A is A's). What the system takes first can't be heard: Shift five times opens Windows' Sticky Keys, Alt alone can focus Firefox's menu bar.
- **Double press** (`DOUBLE_PRESS`, -1 in `holdMs`) is heard only in `useHold.begin`: a second press within `DOUBLE_MS`. A press of a key that also has a double press waits out that window before acting (`doubleKeys`, `keepDouble`).
- **Keybinds Enabled** (this device's) is one gate: `useKeyBinds` answers every action unbound while it's off, so an action added later is covered; Settings → Keybinds alone reads the keys as set (`useKeyBindsSet`).
- A sound or clip on a card answers to a key by the layout's order across both sides (`MEDIA_KEYS`), so a field keeps its key when the card turns.

## The card

**`components/ReviewCard.tsx` is the one card,** drawn by the review, the Layout tab, `CardPreview` and the extension's drawer.

- **A card type's layout is derived, never trusted as kept.** `cardLayout.ts` → `layoutOf(fields, kept)` reads it part by part (a broken bit reads as the field's default, a part for a field gone is dropped, a field added since joins at the end, and when nothing would show on the front the first part does); `over`, `mark` and `subtitles` are kept only where they name a field of the right kind. A type never laid out looks as it always did (`defaultLayout`). A field's side is the layout's (`sideOf`); what knows only two sides keeps reading `side`. `layout.ts` holds the shapes and imports nothing of `type.ts`; what needs a field's kind is `cardLayout.ts`, so the two never load each other.
- **What isn't a field is laid out beside the fields:** the corner marks (`CORNER_MARK_IDS`: the stage tag, the AI's spark, the flag; each corner a row of the marks in it, moved only from corner to corner) and the example arrows (`ExamplesPlace`: a column and the field they follow, by id, so they survive fields added, removed and reordered; null stands right after the example; `examplesIndex`, `examplesAt`). All are kept in `card_types.stage_tag`. A new mark is an id, its shape and kept key, and one entry in `CornerMarks`' list.
- **Turning moves nothing.** Runs of parts that only show once turned (`.review-answer`) hold their room on the front, unseen. A spoiler is `Button variant="spoiler"` over the part, its content `inert`, open until the card goes back to its front. A reading over a word is the word's `<ruby>`, on a line of its own with the reading's room above, its words one box the same size covered or open; a covered reading's button is laid exactly over the `rt` (`position: absolute; inset: 0`), since a button in the line is taller than the words and made the card grow.
- **Playing by itself** (`autoplay`, the review's and the Layout tab's): the parts in view whose `auto` is on are cued one after another in the card's order, each once while the card shows; turning plays what newly came into view. The review keys the card by its id, so nothing carries to the next card.
- **Two columns.** Any part can stand in the side column. On a review 960 px wide or more, a card with something drawn there stands as two: the side column at the left, `--clip-side` of the width, never scrolled; the main column the rest, the one that scrolls. Anywhere else the columns are `display: contents` and each block takes its place by `order`, so the card reads as one column. A layout kept before parts said a column puts the first clip shown as a picture in the side column, from the data (`layoutOf`'s `holdsClip`, which the API answers with `selectHoldsClip`); one saved with columns keeps what it says.
- **Switching examples keeps a clip playing.** `ReviewCard` stays mounted across a switch while each per-example part's `MediaView` is keyed by its value, so the leaving player is replaced. The card hears every `play` in the capture phase and keeps the element each field last played in; a layout effect on every commit reads whether a switched field's element was playing or `ended` before the browser pauses the one taken off the page, and cues the new one to carry on.
- **Players.** Every look (`MediaLook`) plays through `hooks/usePlayback.ts`, so cueing, stopping and failing are one thing. A media element's events don't bubble: whatever hears them listens in the capture phase. Full screen is read off the frame's own root, so a shadow root on someone else's page behaves too. The voice look's waveform is the file's bytes decoded (`waveform.ts`); only the review and the Layout tab hand `ReviewCard` a `waveOf`, so no page's script ever reads a file. Volume and speed are each player's own, keyed by the id of the card type's field it plays (`MediaView`'s required `player`; field ids are UUIDs, so two types never share one), every player of a field following it; kept on this device in `panki.players` (`playback.ts`), a field not set here starting from the old page-wide `panki.volume` and `panki.speed`, which are read and never written. The speed is also set as each element's `defaultPlaybackRate`, which a loading file falls back to. Subtitles on or off (`panki.subtitles`) stays one for the page.
- **A link on a card** is the app's only `<a>`, `LinkView`, whose `href` is `youtubeUrl` of what `youtubeLinkOf` read: nothing typed into a card becomes a link that runs a script or goes anywhere but YouTube. Nothing of YouTube's is embedded or fetched.
- A value is shown as a file only when its field holds files **and** it's an id (`fileKindOf`), so words typed before a field's kind changed still show as words.

## Blur

- **Blur is the front, veiled, never a side.** A card has two sides; while the account's `blurFront` is on, a front whose type marks a part Blur or Hide (`LayoutPart.blur`, `blursFront`) is drawn blurred: each part shown, blurred (`inert`, unselectable; a blurred sound or clip still plays, its picture blurred) or hidden, holding its room, so nothing moves as it unblurs; a clip's subtitles as `blurSubtitles` says. Unblurring fades the blur out and a hidden part in, in 0.18 s, the transitions on the front alone so turning stays instant. A part hidden by the blur plays by itself as the front unblurs, not before.
- **Whether it's blurred is the screen's** (`hooks/useBlur.ts`), by its showing: a review's `turn`, the Layout tab's card. A fresh showing opens blurred; Unblur, Blur and the key toggle it; turning the card leaves its front clear, so Step back returns to it as it stands; Undo puts the card before back clear. The setting off unblurs at once; on again, it blurs from the next showing. `ReviewCard` takes `blur` (blurred, the key, the toggle) and blurs only its front, only as the type marks it.
- **Unblur and Blur** is `BlurButton`, glass (`--blur-glass`, `--blur-edge`) in the card's top-right corner, last in that corner's row of marks so it never covers one; on the back and on a card whose type marks nothing it's held unseen with its room; with the setting off it isn't drawn. `CardPreview` and the extension's drawer pass no `blur`: a card looked at is clear.
- **The spans:** `thinkMs` from the card on screen to the flip (its front, blurred or not), `decideMs` flip to answer, each clamped to the contracts' max; a session left part-way says the side its card stood on (`phase`: front or back). Nothing of the blur is sent or kept.

## The review

- **One screen, two users.** `components/ReviewScreen.tsx` is the review's shell (the counts and their tools, the card in its `ScreenStageContext`, the answers, the phone's tools, the chart, the stage), drawn by `ReviewView` and by the Layout tab (`LayoutView`), never copied. What a review's line is and counts is `reviewLine.ts`, which both read.
- **The line.** `buildQueue` builds the day's line once from the deck's counts and the account's order; `startLine` keeps `pool` cards in play; after each answer `advance` puts a card that comes back (`comesBack`: an ask-again with no wait) where `againPlace` says, or lets the next waiting card in. A new card put aside hands its place to the next new one (`nextFresh`, `joinLine`), but not in a line picked by hand.
- **The session.** `ReviewView` mints its id and `POST`s it as the review opens, or at Start when it opens on today's cards, so leaving from there is no review (a failed start never blocks the review), and ends it as the screen or the page goes (`pagehide`, `keepalive`) or extra study starts, not as the line runs out, so Undo at the end screen stays in it. StrictMode's double mount is covered by a deferred end the remount cancels.
- **Undo** keeps a `Given` per answer (its id, its card, and the line, tally and count as they stood just before) and puts those back; the card goes to its front, clear, as a showing of its own. If the API refuses (`409`), the review lets go of everything it could take back. The editors' Ctrl+Z is separate.
- **Today's cards** (`todayFirst`) are the review's own first state, so every way into a review gets them: the day's line as tiles, every one picked. Starting with all picked keeps the line; otherwise `buildQueue(picked, deck, review, false)`, uncapped. **Extra study** at the end is the same piece (`TodayCards` with `id="extra"`), over the deck's cards never started. The pick is a `pick` row in the ledger, no table of its own; a card left out is untouched.

## The review fits the window

On a computer (`.review.is-fit`, `app.css` → "The review on a computer fits the window") the app is the window's height; the counts and the answers take their own, and the card the rest (`flex: 1 1 0` with `min-height: 0`, since a flex item's `min-height: auto` would let the card grow past the window). The card's parts stand in `.review-body`, centred while they fit (`justify-content: safe center`) and scrolled inside the card when they don't, so the buttons never move and the page never grows.

- **Only the back scrolls.** On the front the body is `overflow-y: hidden` (still a scroll container, so nothing moves as it turns; `clip` would change the horizontal axis); turned back, its scroll is put at the top before it's drawn.
- **A front taller than the room scrolls as itself** (`is-front-tall`, the back's runs `display: none` until turned). CSS can't say whether the front fits, so `ReviewCard` measures it in a layout effect, before anything is drawn, with a pixel of slack so a zoom's fractions never flip it, and again on a `ResizeObserver` of the body and its blocks. A part placed out of the flow is left out.
- **What scrolls shows it with Panki's own fades and thin bar** (`ScrollEdges`), drawn on an element laid over the scroller, never inside it: what's inside a scroller is moved by the browser's scrolling a frame before a script can put it back, so it would shake. The bar shows only for a scroll that follows a wheel, a finger or a key. The body reaches 8 px into the card's padding and pads it back, so a spoiler's cover and a focus ring at its edge aren't clipped.
- **With two columns** the main column (`.review-main`) is the one scroller; a clip in the side column takes the height its other parts leave. **Every other part takes its own height** and the scroller scrolls: nothing is grown to fill the card.
- On a phone the page scrolls, and the body is `display: contents`, as in `CardPreview` and the drawer.

## A review filling the screen

In a review a clip's full screen is the review's: `ReviewView` hands the card a `ScreenStageContext` (`hooks/useScreenStage.ts`), and a player given one turns it. What fills the screen is the review's own `<section>`, which stays while its cards change, so the screen stays filled from one card to the next. `ReviewScreen` marks the staged clip (`[data-staged]`, the part the layout's Full screen shows picks, else the first clip in the Player look not under a spoiler) and draws the review `.is-stage`: the clip `position: fixed` under everything (`z-index: -2`, `isolation: isolate` on the section; nothing it sits in may become its containing block, so no `container-type`, transform or filter above it), and the review in a rail at the right that fits the screen whole; the card scrolls inside itself by the same rules, and the fixed clip neither scrolls nor is clipped with it. Whether it's filled is kept on this device, so a later review fills the screen again. Leaving by the browser's way is kept as leaving; the review reaching its end leaves full screen unkept (the hook remembers the element it saw fill it, since React draws the end out of the ref).

## The Layout tab

`views/LayoutView.tsx` is the review screen with the card editable: the same width, fitting rules and full screen. The card is always live (`ReviewCard` with `edit`): it plays and answers its keys as in a review, and a press on a part picks it (`onClickCapture`, heard on the way down, so a press on its player picks it too). Its settings are `FloatPanel`, inside the review's element so it stands in full screen too, its place kept on this device. The draft is the parts and the marks together, one Undo history. The card blurs as in a review, with its Unblur and Blur, and a part's Blurred front stays live while the account's Start cards blurred is off.

## Files on a card

`CardForm` mints a picked file's id as it's picked; on Add each file goes up first, then the card, so a card never names a file Panki doesn't hold, and a retry sends the same ids. Editing sends only what differs (`changedFrom`). `MediaView` is the one way a file is shown: `preload="metadata"` on a card, `none` on a row, so a long list fetches nothing until pressed; seeking is the API's byte ranges. A clip recorded in a browser often carries no length, so its bar shows the time so far.

## The SRS editor

`srsKinds.ts` is the one registry of the SRS's words and looks, a stage's colour drawn as a tint (`tintOf`: `--tint` mixed by the theme's `--tint-soft` / `--tint-ink`, so one colour reads on every theme). The rules are the contracts', the same the API runs, so the review's buttons say exactly where the card will go. `srsFlow.ts` edits a type by returning a new one; `srsPreview.ts` walks a card through it. **The chart (`FlowCanvas`) is laid out at the zoom (CSS `zoom`), not stretched with `scale()`**: a stretched layer drew blurred text and stray lines in Firefox; only under `G.sharpMin`, where browsers stop shrinking text, is the rest a stretch. An icon in a box is an svg too, so the arrows' sheet is styled as `.sheet > svg`. A built-in type opens read-only: every box opens, every control disabled.

## The frame, themes and the mark

- **The frame is one CSS grid** in `app.css`: on a PC the brand and the tabs share the top bar and the screen's header sits in the 640 px column; under the phone breakpoint the tabs are a bottom bar above the safe area and the header the top bar. One DOM, two placements. `is-wide` (1140 px) widens the column for the SRS editor, the home and Stats; `is-review` gives the review its own. While a field has focus the bottom bar hides (`:has`); what sticks to the bottom sits above it by `--tabbar`.
- **Themes:** `themes.ts` is the registry and the only list (`index.html`'s inline script repeats its ids: `lore.md` → Web traps); `theme.css` gives every token a value per `:root[data-theme]`. "Match the device" is resolved in JS into light or dark, with a `matchMedia` listener only while it's chosen, which also sets the `theme-color` meta. The choice is this device's (`panki.theme`).
- **Fonts** are self-hosted (`public/fonts/`, Urbanist, OFL); Japanese uses the device's own fonts, CJK files being too large to ship.
- **The mark** (パ) is outlines in `brand/geometry.ts`, from Noto Sans JP at 900, drawn as four SVG layers by `brand/Mark.tsx`; `pnpm icons` renders the same geometry into the icon files. **Animation is CSS keyframes, no library.**

## The board and the tiles

`components/Board.tsx` draws the home (doors and chosen tiles in one order, arranged by holding one) and two fixed places in the bar (`TABS`, each with its icon): **Stats** (`/stats`, `views/StatsView.tsx`, every widget but those `streaksScreen`, fixed) and **Streaks** (`/streaks`, the old `/stats/streaks` landing there too; `views/StreaksView.tsx`, Board's `streaks`: the widgets `streaksScreen` (Today), every streak's tile, then `NewStreakTile`, greyed and `inert` while Streaks is Off). Both read the stats through `hooks/useStats.ts`. Widgets are one registry, `widgets.tsx`; every number is the API's (`Stats.windows`, one `WindowStats` per window), the web only divides (a percentage, an average, cards an hour). **Every tile is one anatomy**, drawn by `Tile`: the head (name, the window as `Dropdown`'s `sm`, Show more taking the whole row, not remembered), the figure with its change against `before`, a small `Segmented` of views, the chart (`charts.tsx`: `Columns` plain, stacked or with limit ticks, `Rows`, `LineChart`, `HeatMap`, `Calendar`; the point under a pointer or finger said in the foot), one foot line, the one empty line. A tile's window and view are the device's (`tilePicks.ts`), each pick a `tile` ledger row; Custom…, on every tile with a window, keeps a frame there beside the window `custom`, an amount and a unit picked on `components/FramePicker.tsx` hanging from the window's dropdown (its word "Last", or "Next" for a tile whose entry is `ahead`, Coming up), shown in the dropdown as `frameShort` ("3 w"); the tile asks for that frame's numbers itself (`useFrameStats`: `GET /api/stats?last=` or `?next=` with `unit`, `Stats.custom` or `customAhead`, again whenever the page's stats are), and Coming up draws `customAhead` (`TileInput.next`). No tile breaks anything down by deck: the deck filter over the board does. Every tile reads how a window comes over time from `WindowStats.unit` and `trendUnit`, never from a window's name, so a range of any length draws as the fixed windows do (`stretchesOf`, `byView`; a day alone by the hour). A tile that measures more than one thing declares `measures` (Time watching: Time spent / Runtime watched), drawn as a second small `Segmented` before its views and kept on the device as a view is; Time per card (`pace`) has Front / Back / Total as its views. Activity is one `HeatMap` at `size` "year" for every window (a year's 53 columns fill the width; fewer weeks stand at the left, more scroll sideways under `ScrollEdges` `axis` "x"). **A streak's tile** is one per `Settings.streaks` entry (`streakTileId`, `streak:<id>`), drawn from `Stats.streaks`; its Streak type (Daily / Weekly) is `StreakState.per`, and the tile reads it in one place (`PERIOD_DRAWN`: the row's cell labels, a period said, the period a day falls in; `PeriodRow` draws the seven periods, a week's days or the past seven weeks, `row` and `rowNow` from the API) with the words from `STREAK_PERIODS`; its settings button hangs `components/StreakEditor.tsx` from it for that streak alone (`StreakPanel`, on Streaks and the home alike), saved a moment after each change (`useSavedSoon`, sending the account's streaks as they stand with this one changed, so a streak made since is never sent back without it), with Delete at its foot asking first, the last streak too (`StreakRules` may be empty; deleting the pill's streak sets `pillStreak` null; the home's `fitStreaks` gets an empty list, never one empty id). The dashed tile hangs the same editor over a fresh streak (`NewStreakPanel`), nothing made until Create, greyed at `STREAKS_MAX`. Streaks On / Off heads Streaks; Settings has nothing of the streaks' and nothing of YouTube's (the header bar's streak and the streak reminder are the extension's options page, `architecture/extension.md`). Its Conditions (`groups` of goals in code) are drawn as one list of rows with a joint after each but the last, and / or pressed to flip (`flipped`: an and splits its group there, an or joins two groups), an or drawn as the divider; the groups are all the joints change, never a second control. They offer only the kinds the streak's type fits (`goalKindsFor`), each number up to its kind's most for the type (`goalMax`: a time at most the day's or the week's minutes), and switching the type takes off the conditions that don't fit and brings a number over the new most down to it in the same change (`groupsSwitchedTo`), so the switch is never blocked. A time condition's number is `TimeAmount`: a `NumberField` and a `Segmented` min / h, whole minutes or hours by the half, kept as whole minutes; the unit it opens in follows the value and the pick is the row's while it's open, nowhere kept. Count from sends `"now"` and the API names the day. The tile lists `StreakState.groups`, the nearest to met first, an "or" between them, each condition's state a mark (a `check` in `--good`, the count or a `cross` in `--danger`), with no line under its row. **Today** (`today`, a home layout's `status` read as it through `layout.ts`'s `FOLDED`, in the layout and in the tiles put out, so no board loses it or gets it twice; a `Tile` entry `streaksScreen`: heading Streaks rather than standing on Stats, on the home like any tile) is today's facts (`TodayFacts`: the `today` window's reviews, `started` against its limit, time and watching, cards added, and `Stats.extraToday`) as a `dl`, then, while Streaks is on, every `StreakState` as a row (`StreakChecks`): tinted whole in `--good-soft` with a `check` badge in `--good` once `now`, else `--danger-soft` with a `cross` in `--danger`, at any hour (it never reads `atRisk`, which is YouTube's reminder alone), the time left (`daysLeft` while more than one, else `hoursLeft`) and its run on one line, a pressed line opening each condition of `groups` under it in its own words (`goalRuleWords`) with its own `check` or `cross`, "or" between groups (which are open is the tile's alone). Nothing else in the app reminds: no line over the home, no note on the Review door, no tint on a streak's tile or its map. The home's layout is per device on purpose (`layout.ts`), read defensively (an unknown id dropped, a widget the registry gained arriving put away; old ids folded: `days` into `heat` (Activity), `watch-time` into `watched` (Time watching), the one `streak` into the first streak's tile; each streak's tile put out once, `fitStreaks`; a tile in `PUT_OUT` put out once on each device, at the end or, `afterDoors`, right after the last door, as Today is). On the home (`.board.is-home`) a tile's settings, Show more and Show less are hidden until arranging, a streak's settings panel already open keeping its button. A tile's dropdown is `windowOptions`: the calendar's so far and the spans ending today, each group's first with the rest `under` it, then All time, the custom frame and Custom…; the calendar's come with the spans they match (`windowsOf`), read from `Stats.calendar`; an `ahead` tile (Coming up) has all three under Today, each the rest of it from today to the week's, month's or year's last day, drawn from `Stats.calendarAhead` (`tiles.ts` → `restOf`, `aheadOver`). A streak's Show more picks its own stretch (`STREAK_SPANS`, kept as `TilePick.span`), drawn from every counted period the API sends. **Dragging on a grid** (`useGridDrag`): a copy of the tile follows the pointer by `transform` straight from `pointermove`, no render between; the board draws the order as letting go now would leave it (`dropped`, the same function the drop commits), and the layout is written once, on the drop. Pointer capture is on the root, since the tile's node moves.

## Room on the disk

`apps/api/src/space.ts` is the one place that measures, asking the disk every time (other things fill it too). The home draws `SpaceNotice` while `low`; a failed ask is silent, since a warning must never take the home down. Sizes are the contracts' `sizeWords`, for the terminal and the app alike.

## Skeletons

Every loading state is `components/Skeleton.tsx`, built of the real screen's classes (`conventions/code-style.md`). Counts it can't know are remembered per device in `skeletonMemory.ts` (a deck's rows, extra study's tiles, the Layout tab's chips), so the shape matches what the device last drew.
