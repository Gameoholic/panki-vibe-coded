# The dictionary (step 19, built 2026-10-14, never run)

> **Scope of this file.** The extension's dictionary: its files, looking a word up, the Word pop-up.

> **Never run by Claude** (no browser). The pure parts were checked with `tsx` on a scratch script, outside any browser: 33 conjugated forms back to their dictionary form (探していた, 来なかった, 行っちゃう, 食べさせられた, 勉強しています…), the split with and without frequencies and with a split made by hand, a zip built by hand read back (one file stored, one deflated) and a non-zip refused, rows of each bank read and refused, a formatted definition read as text. Not checked anywhere: IndexedDB, the popup, the page script's registration, any of it in Firefox.

Panki's own dictionary, inside the extension, reading the term-bank zip files most browser dictionaries share. **None of any such tool's code is used** (GPL, and the no-lifted-code rule): the file format was written from its description, the endings from the grammar.

- **Where it's kept** (`dictionary/store.ts`). IndexedDB `panki-dictionary` in the extension's own origin: `dictionaries` (one record each: title, revision, counts, `provides`, `on`, `order`, `ranked`, and `name`, the owner's own name for it, which `shownName` puts wherever a dictionary is named, the look-up's answers included, while `title` stays what tells it apart, from the others and from Panki's copy), `terms` (every word row, indexed by `term`, `reading` and `dict`), `meta` (frequencies and pitch accents, by `term` and `dict`), `tags` (keyed `[dict, name]`). Every row names its dictionary, so one is removed by its rows: its record is marked `removing` first, which takes it off every list and out of every look-up at once, then each store's rows go, in one `delete` of their run of keys when nothing of another dictionary's is among them (an import writes them one after another; one at a time took minutes for JMdict, and the owner thought it wasn't deleting), a key cursor otherwise, and the record last. A removal cut short is finished when the options page next opens (`finishRemovals`). The options page imports and removes; the worker reads. **A page's script never opens it**: its IndexedDB would be the page's own. `unlimitedStorage` keeps the browser from clearing it.

Uploaded in Panki's Settings → Admin by an admin alone (`DictionariesPanel`, several at once, each that doesn't go up saying why; nobody else sees them there), kept for everyone since 2026-10-17 (`shared.sqlite` → `dictionary_files`, the zips in `shared/dictionaries/`; each account's own from before moved there by `gatherShared`), the API reading the zip's index.json, with the same shared reader as the extension, to know what it's called, and since 2026-10-25 counting what it provides from its rows, the extension's own way (`@panki/contracts` → `dictionary.ts` → `providesOf`; the owner: "I have no way of telling which dictionaries may be of use to me"): at upload, and for one kept before, at startup while the API serves (`shared.ts` → `countDictionaries`), kept as JSON in `dictionary_files.provides` and told as `ServerDictionary.provides` (null while uncounted). The options page, signed in, lists those whose title isn't among this browser's dictionaries under "On Panki", each with what it provides as the same "Provides" chips as a dictionary in this browser (without one word's example; "Counting what it provides…" and read again every 5 s while Panki hasn't counted it), and Add (and Add all): the zip is fetched whole through `panki.ts` → `dictionaryFile` and handed to the same `importDictionary` a picked file goes to, so it's checked and counted the same way. - **Reading a file** (`@panki/contracts` → `zip.ts`, `dictionary.ts`, `dictionaryRows.ts`: the rows' shapes and readers, `termRowOf`, `metaRowOf`, `tagRowOf`, moved out of the extension's `format.ts` on 2026-10-25 so the API counts a kept dictionary the same way). Shared since 2026-10-16 with the API, which reads a kept dictionary's index.json with it (Blob, DataView and DecompressionStream are Node's too; the contracts' own typecheck has the DOM library for them). The zip is read here, not by a library: its central directory, then each file through the browser's own `DecompressionStream("deflate-raw")`; only stored and deflated files, under 4 GB (no zip64), at most 256 MB unpacked each, and a file that unpacks to more than it declared is stopped mid-stream. `index.json` and every row are Zod-checked at the door (term banks v1 and v3, meta banks `freq` and `pitch`, tag banks); a row that doesn't read is skipped, and a dictionary already in (by title) is refused. An import that fails part-way deletes what it wrote. Kanji banks aren't read.
- **What a dictionary provides** (`dataKinds.ts`, the owner's ask of 2026-10-16: one list a dictionary gives of the data it provides, in data Panki accepts, each explained where it's named; no guessing). One registry of the kinds of data Panki reads from a dictionary: Dictionary form, Reading, Meaning, Tags, Word type (a row's `rules`, what lets endings be undone), Frequency, Pitch accent, each with its sentence and the popup's parts it's shown in; which card fields it can fill is `roles.ts`'s, each dictionary piece naming its kind. The kinds' ids and the counting are the contracts' (`dictionaryRows.ts` → `DATA_KIND_IDS`, `Provides`, `tallyTerm`, `tallyMeta`), shared with the API. A dictionary's record carries `provides`, how many of its entries carry each kind, counted from its rows at import (`tallyTerm`; frequencies and pitch accents are its meta rows, `tallyMeta`); one imported before that is counted once on the options page (`countProvides`, reading its words 5,000 rows at a time by their keys, which an import gives in a run) and kept (`setProvides`). The options page draws them as `options/DataKinds.tsx` → `KindChips`: on each dictionary's row ("Provides", each with one word's from the dictionary, `options/about.ts`, and its count as a part of all the dictionary's entries, "in 98,112 of 284,196 entries", since a kind carried by entries (`perEntry`) can be on only some of them; a frequency or a pitch accent is a list of its own and says "for 99,999 words"), at the top of the dictionaries ("Panki reads", every kind, faint where no dictionary that's on provides it), and beside the part picked in the popup's layout ("Shows", with the dictionaries it comes from). A chip says it all in the app's `Tip` when pointed at, and the same under the line when pressed. The popup's parts that show one kind go by its name (Frequency, Pitch accent). The language a dictionary's meanings were in was a guess from their letters, and was taken out at the owner's word. Where a dictionary itself comes from is its index.json's own `author`, `url` and `description` under its name (`Origin`; the description is kept from 2026-10-16's imports on, so an older one shows it after it's imported again), and each meaning in the drawer's dropdown names its dictionary (`note`).
- **Undoing endings** (`dictionary/deinflect.ts`). One registry of rules, each `from` → `to`, the kinds the inflected word can be (`is`) and what it becomes. Word kinds are the format's own (`v1`, `v5`, `vs`, `vk`, `adj-i`); four stages (`te`, `ta`, `masu`, `stem`) are only ever undone further, never looked up. Breadth first from the text as found (which may be any kind), each step recorded with its name and the form it was undone from, so the popup can show the chain outwards. `fits(kind, rules)` is the final check against a dictionary row's own kinds (`v5` matches `v5k`, `v5r-i`…). An ending may be the whole word (来ない, 行った) as long as something is left. Rules are looked up by their last letter.
- **Looking up** (`dictionary/lookup.ts`, in the worker). From the letter pointed at: up to 16 letters, never across a stop or a space, every prefix longest first, every form of each, each looked for in the `term` and `reading` indexes (and in hiragana, for katakana written words) in one transaction. Grouped by written form and reading across dictionaries; best first: longest stretch, fewest endings, best rank in a rank-based frequency list, the owner's dictionary order, score. Twelve at most. Tags are read once per dictionary while the worker is awake.
- **Splitting a line** (`lookup.ts` → `latticeOf` in the worker; `split.ts` → `wordsOf` on the page). The worker gives every word that starts at each place, with a cost: `2 + log2(rank + 1)` from a rank-based frequency list (16 in its place when none knows the word), plus half a point per ending. The page picks the cheapest split by dynamic programming; where no word starts, the browser's `Intl.Segmenter` pieces stand in at 30 each, punctuation free. A stretch taken as one word by hand (`Forced`) is always one, and nothing may cross it. The worker keeps what each 16-letter stretch gave while it's awake, so a line written a word at a time is only looked at again near its end. On the page, `dictionary/useWords.ts` holds each line's answer in one store (`useSyncExternalStore`), so the line, the drawer's sentence and a double-click in it split the same text the same way at the same moment; a line is asked about 120 ms after it stops changing, and until then it's the browser's split. The worker's `lookState` answer carries a signature of the dictionaries switched on; when it changes every line is asked again.
