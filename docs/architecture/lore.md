# Lore, security, the machine, deploy and traps

> **Scope of this file.** Implementation lore, the security architecture, the owner's machine, verifying in an isolated instance, deploy, and the traps carried over from the Board.

## Implementation lore

These are the traps that cost real time. Each is load-bearing — re-solve before removing.

- **The shape library tries to run made-up code the moment its first shape is made** (Zod's fast path probes `new Function`). In an extension that's refused, and the refusal is listed as an error against the extension, or reported against the page a script stands on. `z.config({ jitless: true })` only helps if it runs before any shape exists, and the contracts make theirs as they're imported: `apps/extension/src/setup.ts` is therefore the first import of every entry, and the built files were checked for it coming before the first contract shape.
- **A script built as one file gets no `process.env.NODE_ENV`.** Vite's library mode leaves it for whoever consumes the library; React then asks a browser for `process` and the script dies on its first line. `build.mjs` defines it.
- **From outside a shadow root, an event's target is the root's host.** The web's `Dropdown` closed on every press inside itself when put in one, until it looked at the press's path (`composedPath()`) instead of its target.
- **`crypto.randomUUID` only exists on a secure page.** A page's script runs on http pages too; the extension's ids come from `uuid.ts`, made of `getRandomValues`.
- **A message between an extension's parts carries JSON, not bytes** (in Chrome). The clip goes to the worker as base64 and is turned back there.
- **A file read as a data address is cut at its last comma, never its first.** A recording's type is `video/webm;codecs=vp9,opus`, comma and all, and it stands before the text. Cutting at the first comma sent the worker `opus;base64,…`, which isn't base64: the owner's first clip (2026-10-11) died there with "Something went wrong" while its card was added fine.
- **A button that paints no background of its own is grey.** The browser's default `buttonface` fill showed on the tab and chip variants in the screenshots and in no check. `.btn` sets `background: transparent`; each variant paints its own.
- **A box of several lines grows with `field-sizing: content`,** which Chrome has and others don't: `rows=3` is the floor and the fallback, and `resize: none` keeps the browser's grip off it. The phone's bottom bar hides while an `input` *or* a `textarea` has focus (`:has(:is(input, textarea):focus)`), or the keyboard squeezes it.
- **A dispatched click lands only inside the window.** Headless Chrome drops an `Input.dispatchMouseEvent` whose point is off screen; once the type editor outgrew the 900px window, Save was never pressed and the check timed out with nothing to show. `rect()` in `verify.mjs` scrolls the element into view before measuring it.
- **Reordering is pointer events, not HTML5 drag and drop.** Android Chrome starts no native drag from a touch, so one pointer-event implementation (`useDragOrder`) serves mouse and finger; `touch-action: none` on the grip keeps the page from scrolling instead, and the grip takes pointer capture so the row keeps following a finger that strays. A row moved by key loses its focused grip (the DOM node moves), so the hook refocuses it.
- **A tap right after a touch gesture is swallowed.** Chrome drops the click of a tap that lands within about a second of a touch drag's end (its guard against accidental taps): the pointer events fire, no `click` follows, and nothing says why. `dragRow` in `verify.mjs` waits a second and a half after a finger drag; a real finger is never that quick.
- **React's `onWheel` can't stop the page scrolling.** React registers wheel as a passive listener, so `preventDefault()` in it is ignored and the page scrolls along with the chart. `FlowCanvas` adds its own `wheel` listener with `{ passive: false }` to the frame.
- **What a carried tile is over is read from where the tiles lay when the drag began, never from where they are now.** The board redraws itself under the pointer as a tile is carried; ask the page what's under the pointer (`elementFromPoint`) and the answer is the tile's own landing place, which reads as "over nothing", which puts the other tile back under the pointer, and the two trade places for ever. `useGridDrag` measures every slot once, on the lift, in page coordinates so a scroll doesn't shift them.
- **What a body reader's callback throws is nobody's.** Express catches what a handler throws while Express is the one calling it; a function run later, from inside `express.raw`'s own callback when the body has arrived, is called by the stream, and a throw there (a full disk as the file is written) would take the process down. The upload is therefore two handlers in a row (`routes/media.ts`): the first only picks the reader for the file's kind and hands on, the second, called by the router, does the work.
- **A file sent by `res.sendFile` needs `root`.** Without it every part of the absolute path is checked for a leading dot and a data folder under something like `.local` answers `404` for every file; with `root`, only the id after it is looked at. And a callback given to it must stay quiet once the headers are out: a browser skipping through a clip drops the request part-way, which arrives as an error with nothing left to answer.
- **A hoisted function doesn't keep a narrowing.** `const sel = selected; if (!sel) return; function onKey() { sel.split… }` fails to typecheck: a function declaration is hoisted above the guard, so `sel` is still `string | null` inside it. An arrow assigned after the guard keeps the narrowing.
- **The owner's watch-mode API reloads a migration the moment it lands.** `tsx watch` on 3001 restarted when migration 6 was written and ran it on the owner's live data; in the minutes between the contracts change (decks now carry `srsTypeId`) and the API's catching up, their running API couldn't parse its own decks. The migration was proven on a scratch copy of the version-5 schema first and the API files landed in one copy, so nothing was lost — but it is the trap `PREFERENCES.md` warns of, and the next schema step should land contracts and API in one move or with the owner's servers stopped.
- **Windows can't tell `Mark.tsx` from `mark.ts`.** TypeScript resolved `./Mark` to the lowercase file and failed with "differs only in casing". Two files in one folder never share a name up to case; that is why the geometry module is `geometry.ts`.
- **Chrome on a phone paints its own blue tap highlight over whatever was tapped.** On the card-sized review surface it filled the whole card and looked like a broken theme; the checks all passed and only the screenshot showed it. `-webkit-tap-highlight-color: transparent` is set on everything in `app.css`, and pressed feedback is the app's own `:active` style. `pnpm verify` asserts the card's computed value stays transparent.

## Security architecture

The owner self-hosts on a VPS shared with other services, so **containment is the priority** and the realistic risk is supply chain, not app logic.

- **Zero outbound network calls.** No CDN, remote fonts, telemetry. The exceptions are the owner's own decisions, one host each, called by the API alone with the owner's key: Forvo, `https://*.forvo.com` only, for word audio recorded by people (2026-10-15, "Word audio from Forvo", above); and ElevenLabs, `https://api.elevenlabs.io` only, for a video's transcript (2026-10-17, "Transcribing a video", above), the one generated thing Panki makes, named as Panki's wherever it shows; and YouTube's image servers, no key, for a video's pictures kept with a card (2026-10-18, the owner: "can we maybe actually save the thumbnail too?", then the channel's picture): `https://i.ytimg.com` for the thumbnail, from the video's id alone, and `yt<n>.ggpht.com` / `yt<n>.googleusercontent.com` for the channel's picture, from the address the drawer read off the video's page, which the API checks against those hosts and never follows elsewhere (`pictures.ts`, `routes/videos.ts`). Each is fetched once per video and kept in `shared.sqlite` → `video_pictures` for everyone, with where it came from and who asked first; the drawer asks for both as a card is made (`askPictures`), so they're kept while the video is still there, and the app serves them at `/api/videos/:videoId/thumbnail` and `/avatar`. The extension and the web still call nothing but Panki. **Every such call carries a deadline** (`outbound.ts`; `AbortSignal.timeout`: two minutes for a piece at the engine, twenty seconds for anything else), so a service that never answers never holds a request open; one cut short is said as slow, not unreachable.
- **The API binds `127.0.0.1` only.** Nothing reaches it except through a proxy in front of it (nginx, once deployed). The sign-in (above, under "Data model": a cookie whose secret the database never holds, scrypt passwords, a throttle, one database per account) is defence in depth on top of that.
- **Validate every input at the trust boundary** with the shared schema; body size capped at 64 KB. The one route that takes more is a file's upload, read by its own reader under its kind's ceiling (40 MB at most), held to an allow-list of types that a browser plays or draws and that can't carry a script, and believed only as far as its own first bytes; what's stored is served back under the type from its row with `nosniff`, never under a name or a type the sender chose freely. Every answer of the API is `nosniff` and `no-store` (`app.ts`). The sign-in throttle remembers only an address with a wrong try still inside its window, so a scan from many addresses can't grow it (`throttle.ts`).
- **No hard-coded secrets; never log credentials.**
- **The extension is held to the same.** It calls one address, the owner's Panki; it asks the browser for the least it can (one site by itself, the acted-on tab otherwise); a page's script holds no secret and calls no network; what it draws on a page is sealed from that page. Its code is written here, none of it taken from another tool's (`conventions/dependencies.md`).
- Run non-root, unpublished DB, resource-limited, no host mounts once deployed.

## The owner's machine

- **Windows 10**, PowerShell, with Git Bash available. **No Python.** Node 22.14, pnpm 10.
- **`localhost` is slow on Windows:** Node tries IPv6 first, times out, then falls back — about a second per proxied request. Bind to and target `127.0.0.1` explicitly, everywhere.
- **Git Bash `sed` / `awk` can flip a file's CRLF/LF.** Keep each file's line endings consistent.
- **A file still open can't be deleted on Windows** (`EBUSY`). Close a database handle before removing its file — in tests too.
- **The Bash tool truncates long commands.** A file over a few hundred lines is written with the file tool, not a heredoc.
- Chrome is at `C:\Program Files\Google\Chrome\Application\chrome.exe` (override with `CHROME`).

## Verifying in an isolated instance

> **Claude does not run this.** Since 2026-10-10 the owner's rule is that Claude never opens or drives a browser (`CLAUDE.md` → "Never open a browser"). `pnpm verify` stays in the repo for the owner to run if they want to; what follows describes what it does. Its checks have not been kept up with the changes made after that date.

**Never the owner's data or their running servers.** A watch-mode server hot-reloads your edits into their live data.

`pnpm verify` does it the safe way, and is the pattern for every future check:

1. Starts the API on port 3101 with `PANKI_DATA_DIR` pointing at a fresh temp folder, and the web dev server on 5174 proxying to it.
2. Launches headless Chrome with a throwaway profile and talks to it over the DevTools protocol with Node's built-in `WebSocket` — no extra dependency.
3. Drives the real UI: waits for the opening moment to show and lift away on its own, goes through the hub to Decks, opens the new-deck form from the header (empty name first, expecting Panki's own error bubble), adds cards into the deck with `Input.insertText` and Enter, checks the list **and** the API, reviews the deck from its page (two new cards: reveal, the answers say where each goes, answer, the end tallies, the API and `card_places` have the answers, the list shows each card's stage and due time) and back, checks the count and that nothing sits under the list, adds a card from the Add screen with the deck chip, reviews from the picker, visits Settings (steps a setting up and back, reads the change back from `settings_changes`, switches the reviews limit on and off), opens the deck's settings from its row, renames it (and reads the old name back from `deck_renames` straight out of the scratch database), asks to delete and keeps; then card types: opens the starter type, adds a Front field of the Paragraph kind, checks the kind, the side and Required stand in one line at one height and the tools as tall as the name, drags it to a new place by its grip with the mouse (`mousePressed`, moves, `mouseReleased`) and moves it with the arrow keys, saves, checks the deck's form shows a box of several lines, that Enter makes a new line and Ctrl+Enter adds the card, and that the card keeps the line breaks; types a second type out with Enter alone (name to first field, last field to a new one), makes a deck on it, and checks what the API refuses (a used type's delete, a type with no Front, a field of a kind that doesn't exist, a deck on a missing type or a missing SRS type, a card missing a required value, a missing deck, an answer that isn't the type's, a used SRS type's delete); then the SRS: the list, the editor's chart (five boxes), the preview, the rail; a box's menu and a rule change saved on its own (and kept in `srs_type_changes`), the menu closed by its × and by a click on the ground; + on an arrow and Ctrl+Z; a stage's own box (name, wait), renaming on it, a stage's own rules and Sync to default; the Stages list with Burned as a row, removing and adding it back, adding a stage, dragging one, removing one without cards and one with cards (the question, Cancel, then the move checked in the API and `card_places`); an empty name blocking the save; a type from Blank and its delete; a deck switched to another SRS type in its settings (checked in `deck_srs_changes`).
4. Repeats the phone part under `Emulation.setDeviceMetricsOverride { mobile: true }` + touch emulation, driven by `Input.dispatchTouchEvent`, checks `scrollWidth <= innerWidth` on every screen and that the tabs sit along the bottom, reviews by touch, flips Required by touch and drags a field by a finger in the type editor, opens the SRS editor (fits, a finger pans the chart, a tap opens a box's menu and changes the rule, a tap on the ground closes it), then deletes the deck by touch and checks the API hides it while the database keeps the deck, its cards and the removal time.
5. Writes screenshots (desktop and phone, both views) to the temp folder and prints the path. **Look at them.**
6. Stops only the processes it started.

A phone's keyboard can't be checked this way.

## Deploy

Live since 2026-10-17 at https://panki.pro (the repository on GitHub, `Gameoholic/panki-vibe-coded`; the pull-and-restart block is the README, the first-time steps `RUNNING.md`): the VPS behind nginx, under pm2 as `panki-api` on port 4001, deployed from `main` by GitHub Actions since 2026-10-22 (`.github/workflows/ci-cd.yml`: install, typecheck and build on every push and pull request to `main`; a passing push to `main` SSHes in as `panki`, the user that owns the code and the data and runs the API's pm2, with no sudo, whose key can run nothing but the pull, fast-forward only, and `scripts/deploy.sh`: install from the lockfile, build, `pnpm backup`, `pm2 restart panki-api`; the actions pinned to commits, pnpm through Node's corepack rather than a third action; setup in `RUNNING.md`), so whatever reaches `main` reaches the owner's real data within minutes: there are no tests, so typecheck and build are the only gate. Two things the deploy carries since media (step 15): nginx's `client_max_body_size` has to allow the largest file (`40m` a clip; its default of 1 MB would refuse most clips before the API sees them; `200m` for a dictionary zip, `DICTIONARY_MAX_BYTES`); and a backup is the whole `PANKI_DATA_DIR`, the `media` and `dictionaries` folders with the databases, since a row without its file is a card that can't play. **`pnpm backup`** (`cli/backup.ts`, 2026-10-17) is that backup, safe beside the running API: each database snapshotted whole with SQLite's `VACUUM INTO` through a read-only connection (a consistent copy of what was committed; checked on a scratch file with a writer's transaction open), into a folder named for the moment, and every file (immutable under its id) copied once into one `files` folder, so a later run copies only what's new; once a run's snapshot is whole, all but the newest `env.backupSlots` (3, the owner's, 2026-10-22; `backups.ts` → `pruneSnapshots`, which touches only folders named like a snapshot) are deleted, a file in `files` never is, and the folder's size, its snapshots and the newest's moment are a row of the storage report (`space.ts` → `backupsSpace`), and it refuses a folder inside the data (`env.ts` → `backupDir`, `PANKI_BACKUP_DIR`, beside the data by default). **What's paid for is metered** from 2026-10-30: every call to ElevenLabs, Forvo and (from step 2) a Panki AI provider writes a row of the shared store's `usage` ledger, the base for credits and billing later; the keys of each are an admin's in Settings → Admin, or the server's environment (`RUNNING.md`). **Stopping** (pm2's SIGINT): the server stops taking requests, lets those under way finish, closes the databases and exits, or exits as it is after a second and a half (`index.ts`); SQLite's journal keeps every committed write either way, and every write of the browser's is retried safely.

## Traps carried over from the Board (a web app)

Each is load-bearing — re-solve before removing.

**State.** Optimistic UI with the server as the authority. Anything another device must agree on goes to the server; "how this screen looks right now" can stay on the device. No global store until it's needed. When a stored shape changes, old data is normalised on read, never rewritten. Register `/things/reorder` before `/things/:id`.

**Phones and touch.** Nothing may make the page wider than the screen (check `scrollWidth` against `innerWidth` after adding chrome). `(hover: none)` — nothing points; a control hidden with `opacity: 0` still takes a tap. `(pointer: coarse)` — give small targets room with an invisible `::before`; every text field is 16px or iOS zooms. `100dvh` with `100vh` first; the viewport meta's `interactive-widget=resizes-content`. One phone breakpoint, in one place (`app.css`, 640px).

**Themes.** Every chrome colour is a token; a theme is one block that gives the tokens other values. Text on a filled, text-coloured button uses the surface token, never `#fff`. Something pale in every theme sets its own text colour. No flash on load once themes are switchable: an inline script in `index.html` sets `data-theme` before first paint. Native fields need `:where(input, textarea, select) { background-color; color }` from the tokens.

**The browser's own, replaced.** The tooltip is CSS-only. The form is `<Form noValidate>`: on submit it finds the first failing field, focuses it, and says what's wrong in the app's bubble under it. Panels open in the top layer, anchored to what opened them. A field's `autoFocus` is lost if its panel is still `display: none` as it mounts.

**Animation.** Move an element by animating transform from a static anchor, never `left`/`top`. An animation library's inline style beats your CSS — look at the screenshot.

**TypeScript.** `tsc --noEmit` on a "references shell" `tsconfig.json` (`"files": []`) checks nothing. Every package here typechecks its real config.

**Migrations under a running dev server.** The owner's `pnpm dev` runs the API with `tsx watch`, which restarts on every saved edit and runs any new migration step against their real dev data at once. A step is never edited after it's first saved, even before it's committed: a step written in two edits ran half-written on 2026-10-18, was counted done, and its tables never came (the API then failed to start, `no such table: video_pictures`). Write a migration step whole in one edit; any change after is a new step. When a dev store does end up off what the code says, it's put right by hand, once, on that store (that day: the missing tables made, the draft's empty table dropped, `user_version` set to the code's count), never with a step in the code for one machine's mishap (the owner: "I don't want code just to fix this one specific error").
