# Kept up to date without a store

> **Scope of this file.** How the extension is kept up to date without a store.

No store: installed unpacked from a zip Panki hands out, updated by a script, Panki saying when.

- **Two numbers, apart.** Whether an update is *available* is the build's **fingerprint**: `apps/extension/scripts/build.mjs` hashes every file of `dist/chrome` in one order (SHA-256, 12 hex digits), written beside them as `build.json` with `changedAt`, the last git commit day of the extension's sources. The same files give the same fingerprint, so a deploy that changes nothing of the extension says nothing. A Windows build differs from the VPS's for the same commit (line endings), so a PC's build against Prod reads as an update; the Dev profile checks against the dev server. Whether one is *needed* is `EXTENSION_PROTOCOL` (`packages/contracts/src/extension.ts`), compiled into both sides and raised by hand in the same commit as a change that breaks an older extension (`conventions/data.md`).
- **The server** (`routes/extension.ts`; the folder is `apps/extension/dist` unless `PANKI_EXTENSION_DIR`): `GET /api/extension` reads `build.json` afresh each time (a deploy builds beside the running server) and answers it with its protocol; `GET /api/extension/chrome.zip` is the zip. Both answer anyone: the zip is code and nothing of anyone's, and the update script fetches it with no sign-in. `requireProtocol`, before every route, refuses a call whose `x-panki-extension` header is below the server's protocol with 426 before any route reads or writes; no header (the app) or a higher one (a branch's build) passes, and the two routes above always pass.
- **The zip** is made by the server when asked (`zipWrite.ts`: Node's zlib and its CRC-32, no library, no zip64; the last one kept until the build or the address differs). It holds Chrome's build, the Windows script (`Update Panki.cmd`, `update.ps1`), the Mac's (`Update Panki.command`), from `apps/extension/update/`, and `update-from.txt` naming this Panki as the request reached it (`originOf`: nginx's scheme, believed from loopback, and the `Host`), so the script updates from where its zip came from and no address is in the code.
- **The script's rules**, both scripts alike: the address from `update-from.txt` (or asked; `https://` only, or `http://127.0.0.1`/`localhost`); the zip must hold a `manifest.json`; it's copied over the script's own folder **deleting nothing** (a folder Panki was put in by mistake loses nothing) and **never replacing a script or `update-from.txt`**: someone who took over the repository or the VPS could ship a bad extension, which the browser keeps boxed in, but never code that runs on the computer outside it. A new script is put in place by hand. The batch file is one line, read whole before the copy can change it. The build writes the `.cmd` with CRLF and the `.command` with LF (bash reads a `\r` as part of the line). The zip carries Unix modes (`ZipEntry.mode`, `EXECUTABLE` for every `*.command`), since Finder refuses to open a script without its executable bit.
- **The extension** (`updates.ts`, the worker's): checks as the browser starts, on install or reload, hourly on an alarm, when `address` changes, on any 426, and at Check now, each a fresh read of `kept.ts`'s `build` entry. The state (`UpdateState`) goes on the toolbar badge, in literals of `theme.css`'s colours, since the badge can't read the theme. Two builds are told apart: the **running** one, `build.json` as it stood when the code loaded (`noteRunning`, in `chrome.storage.session`, which a reload empties), and the one **in the folder** now, fetched with `cache: "no-store"`; when the folder's is Panki's and isn't the running one, `ready` is true. Reload Panki is `chrome.runtime.reload()` from the worker, answered first; the strip then reloads its page at the video's moment; from the options page, which the reload closes, the page reopens on About (`reopenOptions`).
- **Where it's said** (`ui/UpdateNotice.tsx`, one piece): two numbered steps, because words over a lone Reload button went unread and Reload was pressed as if it updated. 1, double-click Update Panki in Panki's folder, with Find the folder (`chrome://extensions/?id=…`, which says where it's loaded from; an extension can't open a folder or learn its own); 2, Reload Panki, off until `ready`. Manual download (`chrome.downloads`) under them. While one is *needed*, every part of the strip reads as off and its head is that notice alone, open. The options page has `options/Updates.tsx` (`UpdateBanner`, `VersionPanel`); the app has Settings → Extension.
- **Unproven:** a fetch of the extension's own `build.json` seeing the new file before a reload (if not, Reload Panki stays off; the ↻ on `chrome://extensions` still works); the script under a real Windows execution policy and Mark of the Web; on a Mac, Archive Utility keeping the executable bit and the first open being Gatekeeper's prompt (right-click → Open); `setBadgeTextColor` in Firefox.
