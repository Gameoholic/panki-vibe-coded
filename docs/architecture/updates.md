# Kept up to date without a store (built 2026-10-22, never run)

> **Scope of this file.** How the extension is kept up to date without a store.

The owner turned the stores down (a review on every upload); the extension is installed unpacked from a zip Panki hands out and updated by hand, with Panki saying when. Planned with them in the chat and a clickable prototype (https://claude.ai/artifact/SbBEB7JFVxbtLtvkW7rCMN).

- **Two numbers, apart.** Whether an update is *available* is the build's **fingerprint**: `scripts/build.mjs` reads every file of `dist/chrome` in one order through SHA-256 and keeps 12 hex digits, written beside them as `build.json` (left out of what it's worked out from) with `changedAt`, the day the extension's sources last changed (`git log -1 --format=%cs -- apps/extension apps/web/src apps/web/public packages/contracts`, the build's day without git). The same files give the same fingerprint (checked: two builds in a row, the same), so a deploy that changes nothing of the extension says nothing. A build on Windows differs from the VPS's for the same commit (line endings in the sources), so a PC's build against Prod reads as an update; with the Dev profile it's checked against the dev server. Whether one is *needed* is `EXTENSION_PROTOCOL` (the contracts' `extension.ts`), compiled into both sides and **raised by hand in the same commit as a change that breaks an older extension** (the rule is in `conventions/data.md`).
- **The server** (`routes/extension.ts`, `env.extensionDir`, `apps/extension/dist` unless `PANKI_EXTENSION_DIR`): `GET /api/extension` reads `build.json` afresh each time (a deploy builds beside the running server) and answers it with the protocol it speaks; `GET /api/extension/chrome.zip` is the zip of `dist/chrome`, downloaded as `panki-extension.zip` (the day and fingerprint it carried at first went at the owner's word, 2026-10-22; the browser numbers repeats, and the extension's page says which build it is). Both answer anyone: the zip is code and nothing of anyone's, and the Update Panki script fetches it with no sign-in. `requireProtocol`, before every route, refuses a call whose `x-panki-extension` header is below the server's protocol with 426 and "Update Panki's extension to keep using it." before any route reads or writes; a call without the header (the app, an extension from before) or with a higher one (a branch's build) isn't asked; the two routes above are let through.
- **The zip** is put together by the server as it's asked for (`zipWrite.ts`: deflated by Node's zlib with its CRC-32, no library, no zip64; the last one made kept until the build or the address differs): Chrome's build, with `Update Panki.cmd` and `update.ps1` in it, and a Mac's `Update Panki.command` (`apps/extension/update/`, copied in by the build; the batch file's lines made Windows' whatever the checkout gave), and `update-from.txt` naming this Panki as the request reached it (`originOf`: the scheme nginx says, believed from loopback, and the `Host` asked for; the dev server's proxy keeps it, so a zip from `127.0.0.1:5173` names that), so the script updates from where its zip came from and no address is in the code (the owner, 2026-10-22; panki.pro was its default for a day). Double-clicked, the script reads that file (or asks, for a zip without one; `https://` only, or `http://127.0.0.1`/`localhost`), downloads the zip, checks it holds a `manifest.json`, and copies it over its own folder without deleting anything (a folder Panki was put in by mistake loses nothing) and **without ever replacing itself** (`update.ps1`, `Update Panki.cmd`, `update-from.txt` are skipped; the owner, 2026-10-22): someone who took over the repository or the VPS could ship a bad extension, which Chrome keeps boxed in, but never code that runs on the computer outside it. A new version of the script is put in place by hand, from the zip (checked on scratch folders: subfolders merge, the script stays). The batch file is one line run whole before the copy can change it.
- **On a Mac** (the owner, 2026-11-05: "its difficult to run the script… on mac"): `Update Panki.command` beside them, bash doing exactly what `update.ps1` does (the same address rules, `curl -fsSL`, `unzip -oq` into a `mktemp -d` folder, `manifest.json` checked, copied over its folder deleting nothing), the four of them (`Update Panki.command`, `Update Panki.cmd`, `update.ps1`, `update-from.txt`) skipped by both scripts, so neither ever overwrites the other. The build writes it with Unix line ends (bash reads a `\r` as part of the line). The zip carries Unix modes (`zipWrite.ts`: "version made by" Unix, 3 << 8 | 20, and the mode in the external attributes' high half; `ZipEntry.mode`, `PLAIN_FILE` 0o100644 to begin with, `EXECUTABLE` 0o100755 for every `*.command`, `routes/extension.ts`), since Finder refuses to open a script without its executable bit ("you do not have appropriate access privileges"); Windows reads none of it. **Unproven, never seen on a Mac:** that Archive Utility keeps the bit from the zip, and that the first open is Gatekeeper's quarantine prompt, answered by right-click → Open (Settings → Extension's setup steps say so), with no prompt after; files the script copies come through `curl`, which sets no quarantine.
- **The extension** (`updates.ts`, the worker's): asks `GET /api/extension` of the profile's Panki as Chrome starts, as it's installed or reloaded, every hour on an alarm (`alarms`, which wakes the worker), when `address` changes, when any call comes back 426, and at Check now, each a read of the `build` entry of `kept.ts` with `fresh` (below, "What the extension keeps of Panki's"); a page's read is the same entry without `fresh`, so it asks Panki only once the entry is an hour old or the state header says the build changed (a deploy). How it stands (`UpdateState`: current, available, needed, unknown; the running build, Panki's build, when; `ready`) is worked out from that entry and put on the toolbar badge (kept as `update` in local storage until 2026-11-05) ("1" in the accent, "!" in the flag's amber; the browser's colours, so literals of `theme.css`'s two). A failed check leaves the last answer. Two builds are told apart: the **running** one, the folder's `build.json` as it stood when the code was loaded (`noteRunning` on install, reload and startup, kept in `chrome.storage.session`, which a reload empties, since the worker sleeps and wakes many times between), and the one **in the folder** now, read from disk at each ask (Chrome reads an unpacked extension's files afresh; `cache: "no-store"`): when the folder's is Panki's and isn't the running one, `ready` is true, Update Panki (or a zip extracted by hand) having done its part. Pages ask the worker (`askUpdate`, no sign-in, a call to Panki only when the entry is stale) on load, with the focus and every five minutes; an open notice every two seconds, for `ready`. Reload Panki is `chrome.runtime.reload()` from the worker, answered first; the strip then reloads its page at the video's moment (`reloadPage`) to take the new script; pressed on the options page, which the reload closes, the page opens again on its About tab as the extension comes back (`reopenOptions` kept for `onInstalled`). Manual download is `chrome.downloads` (`downloads`).
- **Where it's said** (`ui/UpdateNotice.tsx`, one piece): a button first among the strip's tools while one is available, its panel saying the day and the update as two numbered steps (the owner, 2026-10-22: words over a Reload button went unread, and Reload was pressed as if it updated): 1, double-click Update Panki in Panki's folder, with Find the folder (Chrome's own page for the extension, `chrome://extensions/?id=…`, which says where it's loaded from; an extension can't open a folder or learn its own); 2, Reload Panki, off until `ready`, step 1 ticked then; under them, Manual download, the zip to extract by hand; while one is needed, `active()` reads every part as off (nothing would be answered), `place()` keeps the strip's head, and the head is that button alone, open. The pill's mark gets a dot (`PankiPill`'s `update`). The options page: a panel over every tab (`options/Updates.tsx` → `UpdateBanner`), and on the About tab (Account until 2026-10-22) the build's day and fingerprint with Check now (`VersionPanel`). The app: Settings → Extension (everyone's), the latest build, Download, and the steps to set it up.
- **Unproven:** all of it, never run: that a fetch of the extension's own `build.json` sees the new file before a reload (Chrome's documentation says an unpacked extension's pages are read afresh; if a fetch doesn't, Reload Panki would stay off, and the ↻ on `chrome://extensions` still reloads), the zip in Windows' Explorer and `Expand-Archive` (only `Expand-Archive` was tried, on the built zip: the same 16 files back), the script on a real Windows (its execution policy, Mark of the Web on a first download), `setBadgeTextColor` in Firefox, the alarm across a browser restart, the page reloading itself after Reload Panki.
