# Data model

> **Scope of this file.** The databases, what each table is for, the invariants every table keeps, and how the data changes. The migrations are the truth for each column: `apps/api/src/db.ts` (each account's), `shared.ts` (everyone's), `authDb.ts` (the accounts). The shapes are `packages/contracts/src/`.

## The data folder

`PANKI_DATA_DIR` holds:

- `auth.sqlite`: who the accounts are and which devices are signed in.
- `shared.sqlite`, and `shared/dictionaries/<id>`: what every account shares.
- `users/<userId>/`: one folder per account and the whole of it: `panki.sqlite`, `media/<mediaId>` (the files its cards hold, one per id, no extension; `dbs.ts` → `mediaDirFor`), and `dictionaries/<id>` from before dictionaries were everyone's.

**Every account is a whole Panki of its own.** `dbs.ts` → `createDbs` opens an account's database the first time that account makes a request (`openDb`: the migrations, then the built-in SRS types) and keeps the handle; `closeAll()` at shutdown. `shared.sqlite` is opened once at startup. Every database is WAL, foreign keys on, and a write that finds its file locked waits up to five seconds (`busy_timeout`), since `pnpm backup` and `pnpm space` may hold a file for a moment beside the running API. `pnpm space` opens an account's database **read-only**, so it runs no migration under a server that has the same file open.

Accounts are made only from the terminal (`cli/users.ts`; the commands are `docs/RUNNING.md`'s). The first account made adopts a `panki.sqlite` left at the data folder's root from before accounts existed: moved (with its `-wal` / `-shm`), never copied; Windows refuses to move a file the running API holds, so the command then says to stop `pnpm dev` and makes no account.

## What every table keeps

These hold for every table; a table below says only where it differs.

- **Ids are minted by whoever makes the thing** (the browser, the extension, the CLI), so a retried write is the same row: `INSERT OR IGNORE`, then read back. A file's or a dictionary's SHA-256 tells a retry from other content under the same id.
- **Every time is the API's clock** (`created_at`, `at`), never the client's. The browser only sends spans it measured itself (`thinkMs`, `decideMs`, `shownMs`).
- **Nothing is deleted.** A delete sets `removed_at`, and every read the app goes through filters it out (a removed deck's cards are unreachable too); removing again keeps the first time; a type a deck uses can't be removed at all. A correction or an undo marks the old row (`undone_at`, a fix beside the heard word) and the row stays whole. The one exception: a forgotten service key's row is deleted, since old keys are secrets, not a record (`service_key_changes` says it happened).
- **Every change is a row with the old and the new value,** written in the same transaction as the change; the same value again changes and records nothing (`deck_renames`, `card_type_renames`, `card_type_layout_changes`, `card_type_changes` with the whole type before and after, `srs_type_changes` likewise, `deck_srs_changes`, `deck_settings_changes`, `card_value_changes`, `card_example_value_changes`, `settings_changes`, `admin_changes`, `tracking_changes`).
- **Who did it is on the row** wherever more than one person could have: what everyone shares carries the admin's or the asker's `user_id`, a shared removal its `removed_by`, an undone AI fix its `undone_by`.
- **What happened is frozen; what a thing is, is derived.** An answer's row keeps its session, spans, `miss` and example as they were. A deck's card count, a type's deck count, a card's place, due time, hold, flag and example pin are worked out on every read, never stored, so nothing stored goes stale and retuning a setting never rewrites the past.
- **No `CHECK` on a kind column** (`card_fields.kind`, `media.kind`, `srs_types.after`, `card_holds.kind`, …): the words are the contracts', so a new kind needs no migration.
- `deck_id`, `type_id` and `srs_type_id` are nullable in SQL only because SQLite can't add a `NOT NULL` column without a default; the API always sets them.

## Migrations

Each database has its own ordered list (`MIGRATIONS` in `db.ts`, and one each in `shared.ts` and `authDb.ts`); SQLite's `user_version` counts how many have run, and each runs once, inside a transaction, as the database opens. Each step's comment says what it does and how rows from before read. The rules for writing one:

- A step adds; it never drops a column or rewrites a value it doesn't have to. Old rows are either brought up to the new shape inside the step or read leniently (a JSON column read through its schema with defaults, a NULL read as "from before"), never rewritten elsewhere.
- **The one exception is 53**, the owner's decision for this case alone, made knowingly against the rule above: when the review's phase before the front went (Blur took its place, kept nowhere), it added every answer's and hold's span for that phase into its front's `think_ms` (nothing lost but the column), dropped that span's column from `card_places` and `card_holds` and the type's switch for the phase from `card_types`, wrote a session left in that phase as left on its front, and gave each layout part's key for it the name `blur` (its subtitles' `blurSubtitles`), values untouched; the type logs keep the words they were written in. Its comment in `db.ts` names each column. Checked on a copy of the dev data and by `apps/api/test/migrations.test.ts`. No other step does this.
- A step that ran anywhere keeps its place: one taken back after it ran is left as a step that does nothing (44), so every database counts the same.
- It's written whole in one edit, never edited after its first save (`lore.md` → "Migrations under a running dev server").
- A change to a built-in SRS type is an edit to `srsStarters.ts`, not a migration, unless a stage with cards on it goes away.

## `auth.sqlite`

- `users`: `name` unique ignoring case; `password_hash` is `scrypt$N$r$p$salt$key` (N 2^15, r 8, p 1, a 16-byte salt, a 64-byte key; Node's own), carrying its parameters so raising the cost changes only new hashes; `admin` is set only by `pnpm user:admin`.
- `sessions`: one signed-in device. `id` is the public id the app shows and revokes by; `token_hash` the SHA-256 of the cookie's secret; `device` the browser's description in the app's words (`device.ts`; "Panki extension · …" for a bearer sign-in); `revoked_at` is signing out.
- `login_attempts` (every try, right or wrong), `password_changes` (only the time: a changed password signs every device out), `admin_changes`, `tracking_changes` (each extension sign-in's Video tracking switch, `watching.md`).

## `shared.sqlite`

What every account shares. Anyone signed in reads it; an admin alone changes it, but for what grows as people use Panki: a transcript, a video's pictures, a Forvo word, the usage ledger.

- `service_keys`: one key per service (`forvo`, an engine's id, a Panki AI provider's), read only to call that service. `service_key_changes`: set or forgotten, when and by whom, never the key.
- `dictionary_files`: a dictionary kept on Panki, its zip at `shared/dictionaries/<id>`; title, revision and description from the zip's own `index.json`; one living row per title; removing it deletes the zip (a copy of a file the owner has) and keeps the row.
- `settings`: what an admin sets for everyone, in groups whose keys never meet (`shared.ts` → `Group`: transcription, word audio, Panki AI). Only the keys changed are stored; reading merges them over the group's defaults key by key, and a value that no longer fits its rule reads as the default. `settings_changes` with who.
- `usage`: **the usage ledger**, one row for every paid call Panki makes, never changed or deleted. `kind` is the Admin panel it's shown under; `what` the call (`chunk` / `whole` for an engine, `list` / `recording` / `request` for Forvo, an action's id for Panki AI); `ref` what it was done to; `cost_micros` whole micro-dollars at the listed price as the row was written (`tokenCostMicros`, `soundCostMicros`), NULL for a flat plan. `service_calls` is its predecessor, copied into it and no longer written.
- `video_pictures`: a video's thumbnail and its channel's picture, the bytes in the row, fetched once for everyone, with where from and who asked first.
- `forvo_words`, `forvo_recordings`: every word ever asked of Forvo and its recordings, kept for good (`forvo.md`).
- The transcripts (`transcribing.md`): `transcripts` (one per video), `transcript_pieces` (every piece of sound sent to an engine, paid for whether or not its words stand; `job_id` for a whole video's own pieces, `redo_id` for a part transcribed again; `checked` and `kept` are from when a piece was asked its language, and every piece now is never asked and always kept), `transcript_jobs` (each whole-video download: never cancelled, since it's paid for as it starts; tried at most twice), `transcript_redos`, `transcript_quiet` (a stretch heard with nothing said: covered, no engine asked), `transcript_words` (every word heard, with `logprob`), `transcript_fixes` (a word changed, by hand or by Panki AI, from what it read as to what it says; a word reads as its latest fix not undone), `transcript_line_marks` (a line split or joined at a word; the latest stands), `transcript_forgets` (every ask to forget, even when nothing stood in the stretch). A forget or a redo sets `removed_at` on the pieces and quiet it reaches; a word stands aside when a neighbouring piece heard the same moment farther from its own edge (the stitch), so exactly one word stands at each moment and nothing is deleted.

**Gathered at every start.** `shared.ts` → `gatherShared` moves what accounts still hold from before these were everyone's: the first Forvo key found becomes everyone's (a second account's that differs stays where it is, said in the log); each dictionary's zip is moved and its row made under the same id (one whose title is kept already is let go; one whose zip is missing is marked). Every row dealt with is marked (`dictionary_files.moved_at`, a `moved` row in `forvo_key_changes`), so the next start moves nothing; one account's trouble is logged without stopping the API.

## Each account's `panki.sqlite`

**Card types.** `card_types` carries two JSON columns read leniently by the contracts, so a broken or missing value reads as the default: `layout` (one part per field, in the card's order, each with its blurred front, `blur` and `blurSubtitles`; empty is "as the fields' sides make it", `cardLayout.ts` → `layoutOf`; a part's `showOnPlay` from before is read by nothing) and `stage_tag` (the card's corner marks and the example arrows: the stage tag itself, and `spark`, `flag` and `examples` beside it; `stageTagOf`, `sparkMarkOf`, `flagMarkOf`, `examplesPlaceOf`). `card_fields`: `kind` (the contracts' `FieldKind`); `side`, written from the layout when one is saved and never the other way; `position`, the order in a form (the card's own order is the layout's); `tells_apart` (what tells two cards called the same apart: `CardField.tellsApart`); `per_example` (the field goes with each example, never the field cards are called by); `removed_at`, a hidden field whose values stay.

**SRS types.** `srs_types`: `flow` (answer id → step) and `overrides` (stage id → flow) are JSON; `lesson` is New's own rules (NULL reads as `defaultLesson`'s until saved); `after` and `grow_by` say what the top leads to; `builtin` names which starter a built-in type is; `new_colour`, `description`. `srs_stages`: `wait_n` may be 0 (a stage with no wait); `colour` NULL takes the default ramp; a hidden stage's name stays readable. `srs_answers`: `aside` (set apart from the main row) and `confirm` (asks first).

**Decks.** `type_id` is set once, as the deck is made; `srs_type_id` changes in its settings. `settings` is JSON holding only the `DeckSettings` keys changed, read over `DEFAULT_DECK_SETTINGS` key by key (a value that no longer fits reads as the default). The review keys a deck stored before they were the account's, and `holdAnswer`, stay in it, read by nothing, and a `PATCH` naming them is stripped by the schema.

**Cards.** `cards` is an id, a deck and its times. `card_values`: one row per field given, the value a file's id in a field of files; `source` is where the value came from (`ValueSource`: the owner, a dictionary, a video, Forvo, Panki AI…), NULL on rows from before and read as its card's capture says (`legacySourceOf`). `card_value_changes` keeps `to_source` too, so a change of source alone is a row. `card_sources`: where a captured card came from, one row a card, written with it, never changed; `url` is http(s) only (`CardSource`), so it can never be a link that runs a script; `capture` is JSON (`CaptureFacts`): everything else the extension knew as it made the card, kept for a backfill, read by nothing yet. No video id is stored: a video's cards are found by narrowing `url` with `instr` in SQL and settling with the contracts' `youtubeLinkOf`, so cards from before need no backfill.

**The rest,** each in its own section below: `card_places`, `card_holds`, `card_flags`, `card_examples` with `card_example_values` and `example_pins`, `review_sessions`, `events`, `media` with `media_cues` and `media_recordings`, `forvo_recordings`, `settings` and `settings_changes`. Video tracking's `watch_videos`, `watch_stretches`, `watch_marks` and `saved_videos` are `watching.md`'s; Panki AI's `ai_templates`, `ai_actions` and their changes are `ai.md`'s. `forvo_key`, `forvo_key_changes` and `dictionary_files` are from before those were everyone's and are no longer written.

## The schedule

**A card stores nothing about its schedule but its answers.** Each answer, and each move made for it, is one `card_places` row: when, why (`answer`, `switch` when the deck changed SRS type, `stage-removed` when its stage was hidden), which answer, the place it left and the place it went (`stage_*` a stage id, NULL for New; `past_*` rungs past the top; `node_*` the answers taken inside an ask-again, JSON; `burned_*`). A card's place is its last row not undone. Its **due time is derived on every read**: the last answer's time plus the wait its place has *now* (`dueAt`), so editing a type changes only what happens next. The place is by stage id, so reordering stages moves no card. An answer's row also keeps its session, its two spans, `think_ms` (the front: on screen to the flip, blurred or not) and `decide_ms` (the back: the flip to the answer), its `example_id`, `given_id` (the id the browser minted for that showing: what Undo names, unique where set) and `miss`, frozen as it's given (1 the first main answer when the type has more than one, 0 any other main one, NULL one set apart).

**New is before the first stage, in every type** (`lesson` in the code: `NEW_PLACE`, `isNew`, `LESSON_IDX` -1; `srsKinds.ts` → `NEW_WORDS` is what's shown). It's the place with no stage, not burned, where a new card stands and where a `lesson` step ("New again") sends one. It has its own rules (`SrsType.lesson`). `resolve` clamps a move at the first stage once a card has left New, so only a `lesson` step goes back; a card that lands in New has no wait and no due time, so it's a new card again, counted and lined up as one. The silo tells it apart by the row that sent it there.

**The SRS types that come with the app are rows,** keyed by `srs_types.builtin`. `openDb` makes any a database lacks and, every time it opens, brings each up to what `srsStarters.ts` defines (`makeStarter` under the existing row's ids: stages position for position, answers by name, then by place for a renamed one; written by `updateSrsType`, nothing recorded when nothing differs). The sync never shifts a ladder: a built-in type with more living stages than its starter is left as it is with a warning, since lining them up would move every card. One that fails the type's own rules is left as it is and logged (`lore.md` → Traps). **The key never changes:** Panki Default is the starter keyed `wanikaniPlus`; renaming the key would read as a missing starter and make a second type. Built-in types are read-only (`409` to change or remove). A new type is `copySrsType` of any type, under fresh ids.

**How the rules read:**

- A stage's own rules that equal the default are dropped (`srsFlow.ts` → `edit` ends with `settle`), so "has its own rules" always means they differ.
- `retry` resolves to the same place with a wait of 0. A stored "back to the start" step reads as "go to the first stage" (`upgradeFlow`, run before parsing).
- An ask-again can be `capped`: `againWait` gives the shorter of its own wait and the current stage's; `resolve` and `waitNow` both go through it, so the API, the review's buttons, the preview and the chart agree.
- **Only an ask-again with no wait comes back in the same review** (`reviewLine.ts` → `comesBack`). A stage with no wait is due at once, but for the next review.
- `mainAnswers` are those not set apart: what the preview, the forecast and the answers' colours go by.
- Hiding a stage with cards on it needs `moves`; each card moved gets a `stage-removed` row. Switching a deck's SRS type maps each card by position (past the new top counts as the top; burned stays burned), a `switch` row each.

**Counts.** A deck's `dueCount` is its cards not burned and due by now, under its own `reviewsPerDay` (counted from today's answers that didn't start a new card); `newCount` its cards in New not put aside, as many as its `newPerDay` allows less the new cards started in it today. There's no limit across decks. The day begins at the account's `dayStartHour` in the account's own zone (`zoneOf`; `time.ts` → `dayOf`), so a clock change moves nothing.

**How every review runs is the account's,** not a deck's: the contracts' `ReviewSettings` (`todayFirst`, `newPlace`, `newOrder`, `reviewOrder`, `againPlace`, `pool`, `exampleShown`, `blurFront`), spread flat into `Settings`, each a `settings` row. A deck's own settings are `newPerDay` and `reviewsPerDay`. The order of a review is the web's (`web.md` → "The review").

**Colours.** A stage's `colour` and a type's `newColour` are optional `#rrggbb`; none takes the default ramp for its place (`stageColour.ts`: `STAGE_RAMP`, `placeColour`, `BURNED_COLOUR`), one home for the app, the API and the extension. A New with no colour is drawn plain, with the accent where it's a place on the chart; the review's counts keep the accent, since they name a kind of card, not a place.

## Putting a card aside

Snooze and Suspend (`bury` and `suspend` in the code and the rows) are steps a rule can be, so any answer can do either. `resolve` answers one with the card's place untouched and `hold` set; the API then writes a `card_holds` row (with the answer, its session and spans, `given_id`, and a bury's `until`: made plus its step's wait, frozen as it's made), never a `card_places` one, so the last answer, the place and the due time stay as they were, and the stats never count it as an answer (its seconds count in time spent). A card can also be suspended by hand from its row (`PUT …/hold`). The hold is derived on every read (`db.ts` → `holdOf`): a suspend stands until `lifted_at`; a bury until its `until`, ending by itself with no job and no write. While it stands `Card.hold` says so and `due` is false, so a review, the counts and the Review door leave the card out with no code of their own; a new card put aside leaves room for the next new one. Lifting (`DELETE …/hold`) sets `lifted_at` on every hold that still stands.

## Flags

A flag schedules nothing and puts nothing aside: a fact of its own beside the schedule, on every SRS type. `card_flags` is a row each time it really changes (`flag` or `unflag`, with when, the device, where it was pressed and, in a review, its session), never changed or deleted; the card's flag is its latest row (`db.ts` → `flaggedAtOf`, the one reading every query uses). It stays through answers, holds and Undo. The fields that tell it (`VideoCard.flagged`, `CalledCard.flagged`, `WordsInCards.flagged`, the last meaning *any* of a word's cards) are optional with a default, so an older extension ignores them.

## Undo in a review

Every answer of the session under way can be taken back, newest first. **Nothing is deleted:** the answer's row (`card_places` or `card_holds`) is marked `undone_at`, and every read of where a card stands or what was answered passes over it (`lastPlaceOf`, the `seen`, `lastAt` and hold subqueries of `cardColumns`, `countStartedSince`, `countReviewedSince`, `liftHolds`, the stats): the card stands where it stood, due when it was due, a new card is new again and back in the day's count. Only the time spent studying still counts it (`stats` → `kept`). The API takes back only the last thing that happened to the card; anything since (another answer, a switch, a stage taken away, a hold made or lifted) is `409`.

## A card's other examples

A card's own values are its first example; each one added is a `card_examples` row (its source's columns as `card_sources` has them, NULL for one typed; `removed_at`) with its values in `card_example_values`, holding only the fields that are One per example. They're read with the card as `Card.examples`, oldest first, with their files and cues joined into `Card.files` and `Card.cues`. `valuesWithExample` lays an example's values over the card's own.

**Which one a review shows is pinned, once per review of the card.** `example_pins` is a row per pick (the card, the example or NULL for its own, when), never changed or deleted. `listCards`, what a review reads its cards from, pins each card a review would take now that has examples and no live pin, by the account's `exampleShown` (`pickExample`: Rotate the one after the last pinned, Newest, Random). A pin is live while no answer has scheduled the card since it was made (a `card_places` answer landing outside an ask-again, not undone, later than the pin) and its example is still there: an ask-again keeps it, a hold keeps it, an Undo of the scheduling answer makes it live again. An answer to a pinned card must name the pin (`409` otherwise), whichever example was looked at; turning through them with the arrows never changes it. Nothing about an example touches the schedule.

`videoCards` reads examples' sources too, as a `UNION ALL` with the video's id bound once for each half: a numbered parameter used twice (`?1`) doesn't bind in `node:sqlite`.

## A file on a card

A field of files holds a `media` row's id in `card_values`, like any value, so a card's history and its edits need nothing new. The file is sent first, on its own, under an id its sender minted; the card that names it after. The API believes the file, not the request: its type must be one of `MEDIA_MIMES` (nothing that can carry a script) **and** its first bytes must agree (`mediaFiles.ts` → `sniffMimes`); a container says nothing of what's inside, so the sender names the kind for the field it's going into (`mediaMimeFor`). Each kind has its ceiling (`MEDIA_MAX_BYTES`). The bytes are written under another name and moved onto their own before the row is made, so a failed upload leaves nothing claiming a file is there. A card names only a file its own account holds, of its field's kind. `media.removed_at` exists, and nothing sets it: nothing removes a file.

`Card.files` (file id → `MediaKind`) is derived on every read from the rows each value names, since a Media field takes a clip or a sound and doesn't say which; an id with no row behind it is left out. `media_cues` (what's said in a clip or a sound recorded off a video, timed from its start; read onto each card as `Card.cues`) and `media_recordings` (how a file was recorded off its video, enough to record it again; read by nothing yet) are one row a file at most, written once, never changed.

## Reviews, new cards and studying

The one rule every count follows, settled with the owner on 2026-11-11 (`conventions/in-app-text.md` has the words): **an answer is a review or a new card, never both, and the two are never added together.** A card's first answer, from New, starts it and is a **new card** (`started` on the answer: no stage, not burned, an empty node before it). Every answer to a card already started is a **review**. The time spent on either is **studying**.

- **Counted as reviews alone:** the Reviews tile (number, change, chart, hours, weekdays, stages), Activity's Reviews view, the pill's Reviews today (`Stats.reviews`), the streak condition Reviews ≥ N, a deck's reviews a day in the Review door, and everything that counts what's due: Due now's due, Coming up (`coming`, cards with a due time and not in New), "more come due today", All reviews done.
- **Counted as new cards alone:** the New cards tile, the streak condition New cards ≥ N, a deck's New cards a day (the cards started today come off it), Due now's new.
- **Counted over both, as studying:** Time studying, Activity's Time studying view, Time per card (the typical seconds a card shown took, new or not; its "a card" divides by reviews and new cards each counted once), the condition Time studying ≥ N min, the pill's Time studying today, the days studied.
- **Judged over every answer:** Right and Toughest cards, a new card's first answer among them where it has a right or a miss.

The default streak is "Reviews ≥ 1 or New cards ≥ 1", two groups, so any card answered keeps it, as before the split; the old default kept as it was (Reviews ≥ 1 alone) was made today's once by migration 54, never on read. A new tile, condition or count decides which of the four it is before it's built, and says so in its comment.

## The silo

Everything that happens is kept with its timing, needed now or not: every answer with its spans (`card_places`, `card_holds`), every session (`review_sessions`: `review` or `extra`, its device, when it was left part-way, the card on screen, for how long, flipped or not, and the side it stood on, `left_phase` front or back; no mark of its own, and a `cleared_at` a development database got from migration 52, now a step that does nothing, is read by nothing), and whatever no table is shaped for in the ledger (`events`: `at` the API's clock, `client_at` the browser's for ordering inside a batch, `kind` one of the contracts' `EVENT_KINDS`, `data` JSON, the session's public id and device).

**All reviews done is derived, never stored:** a day counts when an answer (or a Snooze or Suspend given as one) landed on it with no card left due in any living deck within each deck's reviews a day, as `deckCountsOf`'s `dueCount` reads it. It's replayed from the whole history (`cleared.ts` → `clearedMoments`, pure, tested in `apps/api/test/cleared.test.ts`): every place row and hold that stands (`card_places`, `card_holds`, undone ones never happened), in the order kept; each card's due moment set as its place changes, its last answer plus its place's wait under the ladder in force at that moment (the type's logged save then, `srs_type_changes`, the first save's `before` standing for anything earlier, and the deck's type then, `deck_srs_changes`), frozen there so a wait retuned later moves no moment already reached; a card out while a hold stands and from its or its deck's removal; New and burned never due; each deck's reviews a day as `deck_settings_changes` had it, counted per account day. `db.ts` → `clearedOfHistory` gathers the rows and keeps the result while the database is unchanged (`kept.ts` → `whileUnchanged`), so a stats read pays the replay (about 10 ms on the dev history) only after a write. Its cost grows with answers times cards; past what a read can bear, the step is to keep each card's due moment in a heap per deck rather than scanning them all at each answer.

**The stats are worked out on every read** (`db.ts` → `stats(deckId | null, now)` gathers the rows; `tiles.ts` → `tilesOf` works out each window, `streaks.ts` → `streakStatesOf` each streak, both pure) for the living decks in scope, over the account's days and hours (`time.ts` → `dayReader`, `hourReader`; a card overdue counts as due today; the week runs Sunday to Saturday). Each number's definition is the `Stats` and `WindowStats` schemas' comments in `packages/contracts/src/history.ts`; every window (`STAT_WINDOWS`) is worked out for every tile, the web picking, and a custom frame asked for (`?last=` or `?next=` with `unit`, `StatFrame`, an amount of `FRAME_UNITS`) has its days named here (`tiles.ts` → `frameSpan`: the last N units ending today or the next from today, a month back or on the same day of the month held to its last) and is worked out the same way as `Stats.custom` (`rangeFrame`: the window before as many days just before it, its stretches by its length), or ahead as `Stats.customAhead` (`aheadOf`, the coming-due count a day run as far as the frame), nothing of it kept. No number is worked out by deck: the deck filter narrows them all. The ladders are the cards on each stage now; only burned as the 30 days began is replayed, for `burned30`. A deleted card's answers still count among the reviews, the streaks, the days studied and the time, because they happened; it's only no longer named among the toughest cards (`selectScopeAnswers` → `living`). **Time spent studying** is every showing of a card (its front and its back), whatever its answer did (undone, Snooze, Suspend) and a card left on screen, each capped at `CARD_TIME_MAX_MS` as it's worked out (split front, back in that order under the cap; `WindowStats.time.sides`), never as it's kept, so the cap can change and the past reads again under it. **New cards a day as it stood each day** is the deck's `newPerDay` read back from `deck_settings_changes`. **Where the cards stood at a moment** (the Ladder's months, burned in 30 days) is each card's last `card_places` row by then, not undone, on its deck's SRS type as it is now. **A streak** is a rule in `Settings.streaks` (a name, its Streak type, a `STREAK_PERIODS` entry kept as `per`, daily where a rule kept before has none; `countFrom`, `"all"` or the account's day Now was set on, stamped by the API on save (`streaksStamped`: the browser sends `"now"` and never a day; a day already kept stays); and `groups`, goals in groups (Conditions on screen; a period counts when every goal of any one group is met, `groupsMet`; a rule kept with one `goals` list reads as one group, nothing rewritten), each goal a `GOAL_KINDS` entry and a number, a kind fitting only the types its entry's `fits` names; one kept that doesn't fit is read as not there, never refused, so an older rule still reads); which periods counted is worked out from each day's tallies over every deck (`streaks.ts` → `DayTally`: reviews (answers to cards already started), new cards started (their first answers), ms studying and watching, a session cleared), summed over each period and rounded to whole minutes once (`PeriodFacts`), so a rule changed, Day switched to Week included, re-reads the whole past. A period is named by the day it starts on, a week by its Sunday, and `streaks.ts` → `calendarOf` is the one place that decides it. Whether one is at risk is worked out here too, from the reminder's settings and the clock. `Stats.streak` stays the pill's streak for an extension from before; `reviews`, `right`, `days`, `byDay`, `coming`, `added`, `time` and `tough` stay as it parses them.
