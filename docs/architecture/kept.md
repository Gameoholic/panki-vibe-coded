# What the extension keeps, and this browser's own settings

> **Scope of this file.** What the extension keeps of Panki's and how it hears of a change; this browser's own settings and how every page hears of a change.

## What the extension keeps of Panki's, and how it learns of a change

Everything the extension keeps of Panki's is one registry, read again when Panki says a kind of data changed. Nothing kept is trusted for its lifetime alone.

- **The header** (`packages/contracts/src/kept.ts`): every answer under `/api` carries `X-Panki-State`, a hash per kind of `KEPT_KINDS`, as the data really splits: `shared` (the shared settings and which services have a key, `shared.ts` → `kept`), `account` (the account's settings and AI rows, `db.ts` → `kept`), `words` (what `wordsInCards` answers), `build` (`routes/extension.ts` → `buildState`). The account's two only when signed in.
- **Derived from the data, never a counter**: a bump forgotten on one write path is exactly the bug this avoids. Each hash is SHA-256 over the rows as they stand (`apps/api/src/kept.ts` → `hashOf`), worked out again only once the database changed (`whileUnchanged`: `total_changes()` for this connection's writes, `PRAGMA data_version` for another's commits), so most answers read two numbers. The header is written as the headers go out (`stateHeader`, wrapping `res.writeHead`), so it describes things after the request's own change; a hash that fails leaves the header off.
- **No CORS.** The API opens none; the extension fetches with the host's permission, which lifts CORS and its hiding of headers, so no `Access-Control-Expose-Headers` is needed.
- **The extension** (`apps/extension/src/kept.ts`, the worker's): `KEPT`, an entry per thing kept (its kinds, whose it is, a lifetime, how it's asked), in `chrome.storage.session`, each stamped with who, when and its kinds' hashes. `readKept` gives what's kept while it's this sign-in's, inside its lifetime and none of its kinds' hashes differs from the last seen; otherwise it asks. `putKept` keeps a value that came another way (every AI answer carries Panki AI's state); `peekKept` never asks. `panki.ts`, the one network file, notes the header of every answer, refusals included (`noteState`). So an Admin change shows on the next read after any call that carried it; the lifetimes are only a safety net.
- **Outside it:** the thumbnails' glances (`content/feed.tsx`) are the page's own memory, each glance itself a call that carries the header; the running build (`updates.ts` → `RUNNING`) is the extension's own.
- **Unproven:** `total_changes()` and `data_version` through `node:sqlite`; the header read in Firefox's worker. A change landing between an entry's answer and its stamp leaves it stamped with the newer hash, so held until its lifetime.

## This browser's own settings, and how every page hears of a change

The rule: the extension's local settings are loaded first and used locally; nothing of the viewer's waits on Panki. A page that drew in the built-in defaults and switched to the viewer's a moment later is the failure this prevents.

- **One value, one ask** (`messages.ts` → `Local`, `askLocal`): everything of `storage.ts` a page's script draws or behaves by (`prefs`, `source`, `modules`, `known`, `look`, `tracking`, `drawer`), answered by the worker from `chrome.storage.local` alone, with no sign-in and no call to Panki (`storage.ts` → `LOCAL`, `localOf`). A new setting a page reads is a key of the store and a line in one entry, never an ask of its own, and never a field of an answer from Panki. `lookState` stays its own ask: its answer depends on the asking page's address (Panki's own addresses count, and the page never holds them) and on the dictionaries in IndexedDB.
- **Nothing drawn before it's in** (`local.ts`): `loadLocal` asks once (again on a failure, never once the extension is gone from under the page), and a page's script starts everything of Panki's only after it. `localNow` read sooner throws, so a draw that came too early is a fault in the console, never a draw in defaults. A capture asked for from the menu is heard at once and opens its drawer once the settings are in.
- **A change reaches every page at once** (`background.ts` → `tellPages`): on `chrome.storage.onChanged` the worker works out `Local` before and after (`storage.ts` → `localChange`, each changed key put back as `oldValue`) and, only when they differ, sends `LocalChanged` with the whole value to every tab. A page takes it, tells its followers (`onLocal`) and redraws (`useLocal`). A change the page makes itself is on the page at once by `amendLocal`, then kept by the worker, whose word confirms it. The options page reads the storage itself, again on `onChanged`.
- **Still read again with the focus:** only what Panki says, and `lookState`.
- **Unproven:** `tabs.sendMessage` reaching every frame of every tab with Panki's scripts, in Chrome and Firefox; two quick writes briefly drawing the first after the page's own amend.
